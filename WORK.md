## 2026-08-01

- **Procyon mis-decompiles compound assignment.** `x += (int)(expr)` has TWO sources; disassemble each site. `i2f`/`i2d` on the LHS before the add = artifact, rewrite as `x = trunc(x + expr)`. Truncate-then-`iadd` = genuine, leave alone. ~45 sites in the keep set, 23 in `Mad.java`.
- **`*= (int)<float literal>` is ALWAYS an artifact.** `r3 *= (int)0.991` (black skybox) and `r6 *= (int)1.6` (checkpoint flash) are really `r3 = (int)(r3 * 0.991)`. Nobody writes a multiply-by-truncated-literal; don't "preserve" it as a game bug.
- **Every int op wraps at 32 bits, including the addition.** `Math.imul` on the terms is not enough — wrap the whole expression: `i32(Math.imul(a,a) + Math.imul(b,b))`. Reachable in practice: stage coords run to ±83000.
- **`Medium.sin`/`cos` return `float`.** Any expression touching them is float32 in Java; needs `fr()` at EACH binary op, not just at the end. Missing one drifts over frames instead of failing.
- **`Medium.random()` bottoms out in unseeded `Math.random()`.** `contO.zy`/`xy` are therefore NOT reproducible from a Java probe — three identical runs gave different values. Run any probe 3× before calling a mismatch a port bug.
- **In-race tick rate is 530ms per 10 frames (53ms, ~18.9Hz).** `GameSparker.java:1708`, `n5 = 530`. The 400ms figure is the MENU branch. Using 400 runs the game 1.325× too fast.
- **`java.awt.fillPolygon` is EVEN-ODD.** Checkpoint glyphs are keyhole polygons (bridge out to the counter and back). Ear clipping only works when the inner loop winds opposite the outer — true for "R", false for "O". Use a scanline even-odd fill.
- **No depth buffer anywhere.** Submission order IS depth. Never reorder, batch by material, or split primitive types into separate draw calls.
- **A default-constructed `CheckPoints` makes `Mad.drive()` hang forever.** `typ[]` all-zero spins `Mad.java:1600`; `nsp == 0` spins `Mad.java:1578`. Any probe must set `typ[]` positive and `nsp > 0`.
- **Don't `Unsafe.allocateInstance` a `ContO` for probes.** Constructor never runs, every reference field is null, and `drive()` NPEs on a different one each time you patch the last. Build it from a real `.rad` out of `models.zip`.
- **Verification pattern that works:** unpack `Game.jar`, drive the real class by reflection (`setAccessible(true)`), print state, diff against JS as exact integers. Probes live in `web/tools/`. `MadProbe` declares `package tools;` → run as `tools.MadProbe`.
- **`loadbase` self-checks:** summed uncompressed size of `models.zip` must equal 615671, else `mload = 2`.
- **Delegated transpilation jobs edited tests to make them pass — twice.** Never trust a green suite or a "gaps: none" report from a subagent; diff against an independent artifact and check the baseline file's checksum. `CarDefine.loadcar` was also silently stubbed to `return -1` (its own failure code) while the report claimed only networking was dropped.
- **`agy` quota is shared across `claude-*` and `gpt-oss`; gemini is a separate pool.** Run jobs ONE AT A TIME — five parallel opus jobs exhausted the quota and killed all five mid-flight.
- **Render resolution is free; tick rate is not.** The vertex shader divides by `u_size`, so raising the canvas backing store costs zero CPU. Raising the tick rate doubles game speed, because every constant in `Mad.drive()` is per-tick.
- **`ContO.d()` is not pure either, per OBJECT.** `fixit()` steps `fcnt` and clears `fix` once it passes 7; `pdust()` steps the `stg[]`/`rtg[]` particle stages to 10 and then clears them; `electrify()` walks its own counters. All are driven from `d()`, so an interpolated frame advances them at display rate — the repair sparkle ran fast and could step straight past the frame that clears `fix`, leaving a car sparkling until the next repair, while landing dust ran through all ten of its stages inside one tick and was never seen at all. Snapshot/restore per-object animation state alongside the transform (`OBJ_STATE`/`OBJ_ARRAYS` in main.js), the same way `MED_STATE` handles Medium. Arrays must be copied element-wise — storing the reference restores nothing.
- **`GameSparker.draw()` is NOT pure.** It calls `Medium.d()`, which toggles `cpflik`, recomputes `elecr`, decrements `noelec` and advances `lilo`. Re-running draw at display rate for interpolation advances all of them 3× too fast — snapshot and restore them.
- ~~**Measured cost split (stage 1, 7 cars, ~8.9k tris):** `simulate()` 10.3ms, `draw()` 3.1ms.~~ WRONG — see the 2026-08-01 re-measurement below. Both the split and the triangle count were off.
- **"Render resolution is free" is WRONG** (entry above, superseded by measurement on the target machine). Vertex work is free; fragment bandwidth is not — no depth buffer means the painter's algorithm overdraws the whole scene, so 2x = 4x the overdraw. `antialias:true` multiplied it again, and the 2D overlay's per-frame full-size `clearRect` was a CPU cost that also scaled with `?res=`. Overlay is now sized by `?textres=` (default 1) and MSAA is off above 1x.
- **The static host sends no `Cache-Control`.** An ES module graph then goes stale one file at a time: you get the new `main.html` and last deploy's `graphics.js`, and the change looks like it didn't ship. `deploy.sh` stamps every relative import and `<script src>` with `?v=<md5 of sources>`.
- **Real cost split, measured in-browser (stage 1, res=2):** 1 car — sim **0.61ms**, draw **14.60ms**, 47k verts. 8 cars — sim **1.72ms**, draw **24.38ms**, 100k verts. Physics is 2-7% of the tick; DRAW IS EVERYTHING. Cost tracks vertex count at ~0.25µs/vert. Static stage geometry is ~40k verts, re-projected on the CPU every frame though it never moves.
- **Draw layers, measured properly (8 cars, res=2, ns/vert normalised):** overlay **1.8%**, geometry batching **19%**, projection/traversal **81%**. This SUPERSEDES the ~50/50 figure below, which credited a lighter scene as a saving because `raster=0` reported zero verts and could not be normalised.
- **Cost model from two browser runs:** `draw = ~9.8ms fixed + ~1.01us per PROJECTED vertex`. Projected != submitted: `Plane.d` transforms 12-20 vertices per face (the `master===1` LOD switch) before culling decides whether to submit any, so 14,799 vertices are projected to submit 10,263 (1.44x). Node agrees on the slope (0.65us) but shows only 1.4ms fixed; the browser's 9.8ms fixed term is NOT accounted for -- `medium.d()`, the backdrop, is only 1.8ms/16%.
- **Nothing counts the even-odd scanline fill's cost, which is proportional to polygon AREA, not vertices.** Checkpoint glyphs on screen in one run and not another moves the fixed term with no counter changing. Suspect this before trusting a fixed-cost figure.
- **Array pooling is a 30% PESSIMISATION** (10.96ms -> 14.27ms, node, same scene). The "1.13x, bit-identical" entry above was wrong, and the in-game A/B that appeared to show no difference compared fps -- which is pinned at 18.9 with `interp=0` and could not have shown anything. Leave `?pool=` off.
- **Scene shape is reproducible in node to within 0.1%** (faces 1956/3261 for 1/8 cars, matching the browser exactly). Use `web/` under node to get counts and ratios without a browser round trip; only absolute timings need the real thing.
- **Draw splits ~50/50 between projection and the batcher** (8 cars, res=2, `?raster=0` isolates it): 24.09ms normal vs 12.53ms with the emit calls no-op'd. So per-vertex projection in `Plane.d` is 12.5ms and triangulation + vertex-buffer writes in `graphics.js` are 11.6ms. Moving projection alone to a vertex shader is worth ~2x, not 4x.
- **Timing `GameSparker.tick()` as a unit reports `draw 0.00ms`.** `tick()` is `draw()` then `simulate()`, so with interpolation off the entire draw cost lands in the "sim" number. Time the two halves separately — this is what produced the bogus 10.3/3.1 split above.
- **With `interp=0` the game draws only on a tick, so fps is pinned at 18.9 by construction.** Comparing render settings by fps in that mode always reads flat; use the ms figures. Interpolation is now the DEFAULT (~58fps measured); each interpolated frame still costs a full CPU redraw, so draw cost is what caps the frame rate.
- **`Medium.follow()` is a stateful ease, not a function of time.** Re-running it per interpolated frame gives one ease step from the restored tick state every frame, so the camera lurches once per tick no matter how smooth the objects are. Interpolate the camera's own two tick states instead. The `cam=derive` mode built on this was removed.
- **`Math.imul` on a float operand silently zeroes it.** `Mad.colide`'s narrow-phase threshold is `(n3 + n4) * (comprad[a] + comprad[b])`; `comprad` is a `float[]` (formula7 = 0.4), so the port's `Math.imul` truncated the sum to 0 and the threshold became 0 — **no car in the default field ever collided**. Use `Math.imul` ONLY when both operands are `int` in the Java; check the field's declared type, don't infer it from the values. Audited: `CarDefine.powerloss` was the only other candidate and is genuinely `int[]`.
- **Two identical cars never collide, and that's authentic.** `colide()` picks a dominant car by `|power * speed * moment|`, then by `moment`; on an exact tie neither dominates and no contact is evaluated. Any collision test must make the two cars asymmetric or it silently tests nothing.
- **The concave fill was emitting one quad per pixel ROW.** Replaced with a trapezoid decomposition (cut at every vertex y AND every edge-edge intersection y, one trapezoid per span per band): 40,041 -> 25,455 verts/frame, 8.4% CPU. Both are exact even-odd; verified against a point-in-polygon truth, not against each other.
- **Backdrop quads arrive ordered TL, TR, BL, BR — bowties.** `java.awt` fills those as an hourglass, so even-odd is REQUIRED and a triangle fan would fill the bounding quad. Any fill rewrite must keep intersection ys as band boundaries or the left-to-right span pairing is wrong inside the band containing the crossing.
- **`medium.d()` (the backdrop) was 6.38ms/frame, 34% of draw** — and it was mostly the scanline fill, not the band geometry: the trapezoid fill took it to 3.83ms (-37%) with no other change. Confirmed in-browser at matched scene weight (9,519 vs 9,476 submitted verts): emitted 57,069 -> 37,269, 2146 -> 1888 ns/vert. The "fixed cost that scales with nothing" was largely an O(polygon height) term.
- **A within-run regression of draw-ms against scene weight is ill-conditioned.** It returned a NEGATIVE fixed cost (-3.44ms) and a higher slope for a run doing strictly less work. Slope and intercept trade off when the x-range is narrow. Report R^2 and the x-range, and prefer a direct stopwatch (`?prof=1`) over a fitted intercept.
- **`loadbase` puts track pieces at slot `j + 56`, not `j + 16`.** Cars are 0-15 but there is a gap before the track models. Assuming they were contiguous mislabelled every placed object and silently defeated a filter that keyed on the name. Import `CAR_NAMES`/`TRACK_NAMES` from `GameSparker.js` rather than copying them.
- **`Medium.trk !== 0` is what makes an overhead view possible.** `ContO.d`'s distance-fade and minimum-projected-size culls are both written `... || this.m.trk !== 0`, so at map zoom only 7 of 190 objects survive with `trk = 0`. `trk = 2` is the StageMaker's overhead editing mode (`StageMaker.java:886`) and keeps decor; `trk = 1` hides it.
- **The stage knows its own extent; don't infer it from object positions.** `maxl`/`maxr`/`maxt`/`maxb` in the stage file are the four boundary walls, and `loadstage` passes exactly those to `trackers.devidetrackers()`. So after a load, `trackers.sx / sz / ncx*3000 / ncz*3000` IS the game's own bounding box. Deriving one from object positions is both wrong (outliers skew the centre) and unnecessary.
- **The renderer cannot do a whole-stage overhead view of a large stage.** The StageMaker's own overhead mode stops at `m.y = -15000` and SCROLLS. Stages 1/3/9 render at ~67-81k depth; stage 8 at ~91k emits 24 verts for 172 objects that pass every gate checkable by hand. Cause is inside `Plane.d` and is NOT understood. The launcher falls back to a flat map past 85k.
- **`ContO.d`'s `crs` shadow assumes the object sits on a track.** A car floating at `y = 0` gets the silhouette drawn across its middle; seating it at `y = ground - grat` (what loadstage does) makes the shadow the entire frame. Previews should just turn `shadow` off.
- **`Medium.sin`/`cos` are 360-entry tables indexed by WHOLE degrees**, so an interpolated frame could not express a heading between two degrees and had to round. At ~800px across a ~60-degree view that is ~13px of yaw per step: interpolation translated smoothly but rotated in 13px jumps, which is why `?interp=1` was jittery ON TURNS AND ONLY ON TURNS. Both now lerp between neighbouring entries for a fractional argument; an integer argument takes the identical branch, so the simulation is untouched and stays bit-identical.
- **`xtGraphics.playsounds()` is the per-tick sound pump, and nothing works without it.** It decrements every `bfXXX` debounce counter (`xtGraphics.java:9207-9221`) and drives the engine loops via `engs[][].checkopen()`. Porting `crash`/`skid`/`scrape` alone gets you exactly ONE of each per session, because the counters they set are never cleared. Called from `GameSparker.java:1705`.
- **The HUD is drawn from `simulate()`, not `draw()`, and it is BOTH kinds of drawing.** Labels and images go to the 2D overlay; the damage/power bars and the checkpoint arrow are GEOMETRY in the same batch as the scene. Both are emitted once per TICK, so an interpolated frame drops both unless handled: keep the overlay (`begin(true)`) AND replay the geometry `simulate()` produced (`snapshotFrom`/`replay`). Fixing only the overlay left the meters reading zero and the arrow missing — the failure looked like a game bug rather than a frame-composition one.
- **A canvas keeps one context type for life,** so a 2D fallback cannot share the WebGL canvas -- `getContext('2d')` returns null. And an author `canvas { display: block }` beats the UA stylesheet's `[hidden]`, so a hidden canvas still takes up space.
- **Headless Chromium won't run rAF without `--screenshot`.** `--headless=new --virtual-time-budget=N --dump-dom` boots the page, runs GL, and never fires a single animation frame, so the game appears hung. Adding `--screenshot=x.png --window-size=800,450` drives the compositor and it runs. This is the cheapest way to verify a browser change end-to-end (`--enable-logging=stderr --vmodule=console=1` to read `console.log`).
- **Draw-driven effects break in TWO ways under interpolation, and the counter is the lesser one.** Effects roll their SHAPE from `random()` on every call, so an interpolated frame drew a DIFFERENT random shape, not a later one — the repair ring's electricity buzzed at 58Hz instead of arcing at 18.9. No snapshot in `main.js` could ever have fixed that. Fixed centrally instead: `Medium.random()` records the tick draw's sequence and replays it during an interpolated pass, armed in `Medium.d()` (always draw's first call). Do NOT cache per call site — `Plane.s()` alone has ~30 shape-rolling randoms. Counters are the other half, guarded at the mutation with `medium.interpolating`. `OBJ_STATE`/`OBJ_ARRAYS`/effect-`MED_STATE` are gone; `main.js` now snapshots draw's one genuine OUTPUT, `ContO.dist`.
- **The old per-field snapshot list was structurally incomplete, not just missing entries.** It could only ever name the effects already reported broken; `elc`/`edl`/`edr` never got added, `dsprk` was reseeding 100 sparks per interpolated frame, `Plane.s()`'s entire damage animation (`embos`, the `chip` debris and its velocity integration) was never covered, and nothing covered the randoms at all. If you add an effect that mutates from inside `d()`/`s()`, guard it at the mutation — `integration.test.js`'s "an interpolated draw advances no per-effect animation state" fails if you don't, and also fails if two interpolated frames of one tick differ by a single vertex.
- **`Plane.s()` is an animation system, not just a projector.** It steps `embos` 16→70 (the crumple/burn stages), spawns and integrates the `chip` debris shard (`dx += vx`, `vy += 7`, stage to 20), and rolls ~30 randoms per face for panel jitter, flame triangles and `flx` flicker. Anything that re-runs draw has to account for it; a grep for effect state that stops at `ContO`/`Medium` misses the biggest one.
- **`playsounds()` is now ported and called from the END of `GameSparker.simulate()`,** not from the draw half — it is per-TICK. Putting it anywhere an interpolated frame reaches would chatter the engine loops and run every `bfXXX` debounce down ~3x too fast. Two tests guard it, one of which asserts the tick actually CALLS it: porting the method and forgetting the call site passes every other test and changes nothing audible.
- **`AudioClip.loop()` needed a real looping clip type, not repeated one-shots.** `sparkeng()` holds exactly ONE of five engine samples looping and switches which as the revs cross a band edge, so `loop()` on an already-looping clip must be a no-op or the engine machine-guns at the tick rate. `web/audio.js` keeps loops in a separate map from one-shots (`stopLoop` vs `stop`), and `setMuted(true)` has to cut live loops — gating new playbacks alone leaves the engine running under the mute.
- **`Data.js`'s buffer MUST be an Int8Array, and the constructor now coerces.** Java's `byte[]` is signed and ibxm leans on it: `sByte()` returns the raw element, so handing it the `Uint8Array` that `vfs.js`'s zip reader produces read 130 where Java reads -126. The sample decoders survive it by luck (`<<8` into an Int16Array is modular, so 130 and -126 agree), which is what makes it dangerous — in ibxm that value is a sample's FINETUNE, so the symptom is a detuned note and nothing thrown. Delegated jobs will not catch this: the test constructed an Int8Array by hand and passed.
- **Node's `TextDecoder` has no `Cp850` label, and falling back to Latin-1 is NOT porting the Java's fallback.** The Java only falls back when the charset is genuinely absent, which on a normal JVM never happens, so the fallback path is dead code there and taking it here is a divergence (visible on bytes >= 128: 0xD6 is Í in Cp850, Ö in Latin-1). `web/ibxm/Data.js` carries the 128-entry table printed by the JVM itself.
- **Probes must print strings as CODE POINTS, not as text.** A high byte does not survive the terminal on the way out plus the editor on the way in: the first `DataProbe` printed Cp850 text and the expected literals landed in the test as UTF-8 for a different character, which then had to be debugged as a fake mismatch.
- **`idiv(x, 0)` returns 0 where Java throws ArithmeticException.** Applies to EVERY `idiv` site in the port, not just the one that surfaced it (`Envelope.calculateAmpl`, where `dt` is 0 if a module puts two envelope points on the same tick). Java crashes; the port silently produces 0, which in a browser is the better failure but is NOT the Java's behaviour. Deliberate, and only reachable on malformed input — but if a ported class ever looks like it is quietly tolerating bad data where the jar dies, this is why.
- **The engine, skid, scrape and crash sounds are confirmed correct by ear (2026-08-01)**, in a real browser, after `playsounds()` landed. Worth recording because no test can establish it: the suite proves `sparkeng()` switches to the right clip index and that the `bfXXX` counters clear, and both can be green while the result sounds wrong. Audio changes need a listen, not just a green run.
- **The music is PRE-RENDERED, not streamed — there is no realtime tracker playback in this game.** `RadicalMod`'s constructor runs `IBXModSlayer.turnbytesNorm()`, which mixes the whole module to a PCM `byte[]` at load (16-bit LE, MONO — it keeps only even mix indices, one side of the stereo pair — 22000 skiprate, capped at 18MB) and hands it to `SuperClip`, a plain streaming clip with a loop point. So the browser needs an AudioBuffer and a looping BufferSource, NOT an AudioWorklet: no ring buffer, no realtime deadline, no audio-thread concurrency. `MUSIC_PORT_SPEC.md`'s original wiring plan was wrong about this and is corrected. It also makes the oracle a single byte-for-byte buffer diff.
- **The game reaches ibxm through a wrapper layer the music spec missed:** `RadicalMod` (208) -> `ModuleLoader` (79) -> `IBXModSlayer` (110) / `IBXMod` (30), ~427 lines on top of ibxm's 2,494. `SuperClip` (126) is deliberately NOT ported — it is Java Sound streaming that `web/audio.js` replaces.
- **The music does NOT need the ibxm port: BassoonTracker (pure JS, 16.3 KB gzipped, vendored in `web/vendor/`) plays the game's own `.mod` files directly.** 3.3 MB of modules already in the repo, against 54 MB of Opus / 203 MB of FLAC to pre-render them or ~2,500 lines to port the tracker. `BassoonTracker.processFile(arrayBuffer)` is the in-memory entry point (`load()` just fetches to an ArrayBuffer and calls it), so modules go straight from `vfs.js`'s zip reader with no build step. Not sample-identical to ibxm's mixer, and it uses a deprecated `ScriptProcessorNode`.
- **Importing `web/vendor/bassoonplayer.js` DEFINES `window` and `AudioContext` as globals**, even under node. So `typeof window === 'undefined'` is useless as an environment check anywhere downstream of that import — it reports "browser" under node, and the tracker's init then dies on a stub with no `createGain`. Detect audio by TRYING to init inside a try/catch and remembering the failure, not by feature-sniffing globals.
- **`trackvol` is not a volume multiplier for stock stages.** `loadstrack` takes it but only uses it in the custom-track branch (`stage < 0`), where it IS the gain for a `mystages/mymusic` track; stock stages use their own per-stage constant. Scaling stock stages by `trackvol/200` double-counts — invisible today only because nothing but the example mystage sets it, so it is always the 200 default.
- **`deploy.sh` copied `web/*.js`, which silently SKIPS subdirectories** — so `web/vendor/bassoonplayer.js` was absent from the deployed tree and the page hung forever on "booting...". A failed ES module import throws, so `boot()` never completes; and the browser reports the missing file as `blocked because of a disallowed MIME type ("")` rather than as a 404, which sends you looking at server config instead of at a file that was never uploaded. `music/` was missing for the same reason (it was never needed until the soundtrack was wired up). Both are now copied explicitly. Anything added under `web/` in a subdirectory needs a line in `deploy.sh`.
- **Test the STAGED tree, not the repo, when a deploy problem is suspected.** Serving the repo root passes happily while the deployed tree is broken, because the repo has the files the deploy is missing: build the staging tree the same way `deploy.sh` does, serve that, and boot it headlessly.
- **The car-select stat bars are ABSOLUTE, not a ranking** (`xtGraphics.java:6096-6131`). Six bars, each a fixed formula clamped into 0..1 — `(swits[2]-220)/90` floored at 0.2, `acelf[1]*acelf[0]*acelf[2]*grip/7700`, `dishandle`, `(airc*airs*bounce+28)/139`, `(moment+0.5)/2.6`, `outdam`. The launcher had four stats normalised against the roster maximum instead, so every bar disagreed with the game and one car always read 100%. Also note the game `fillRect`s the bar's REMAINDER black: the drawn rect is `1 - value`, so reading the fill width off the disassembly inverts it.
- **`sortcars` is undefined past stage 27, and stages 28-32 are the MULTIPLAYER stages** (`Lobby.java:3839` labels them "Multiplayer - Stage 1..5"). The forced opponent `7 + (n-10+1)/2` is 16 at stage 28 and the sampler's `24 + 8*((n-10)/17)` reaches 34, which `-= 16` only brings back to 18 — either way `models[sc[j]]` is null and `loadstage` dies on `.grat`. The Java never reaches it: stage select clamps to 27 (`xtGraphics.java:1899`, and the right-arrow guard at `:2597` won't increment past it), and in multiplayer the grid comes from the network so `sortcars` isn't called at all. The port lets you pick 28-32 solo, so it clamps `n` to 27 for the opponent pick only.
- **Setting `masterVolume.gain.value` on BassoonTracker does nothing, silently.** `audio.setMasterVolume` drives the param with `setValueAtTime` + `linearRampToValueAtTime`, and an AudioParam under automation ignores later `.value` writes — so the write succeeds, reads back correct immediately, and is inaudible. The tracker also calls `setMasterVolume(1)` on play and for MOD effect 0x10 (global volume), overwriting anything set before playback. `?musicvol=` therefore had NO audible effect at any value, and the fixed trim constant alongside it was equally inert — which is why halving it twice changed nothing. `music.js` now wraps `audio.setMasterVolume` and scales every call. Measure this by reading `masterVolume.gain.value` a few seconds AFTER playback starts, not right after writing it: both the broken and fixed versions look correct if you read immediately.
- **A frame cap whose deadline is set from `now` undershoots badly.** `nextFrameAt = now + 1000/MAX_FPS` folds each frame's overshoot into the next deadline, so on a 60Hz display the deadline drifts past a vsync and waits for the following one: `?maxfps=30` measured ~20-23fps, `maxfps=60` ~38. Advance the deadline by a whole interval from the PREVIOUS deadline and allow ~2ms of slop for rAF timestamp jitter (a deadline missed by a fraction of a millisecond otherwise costs a whole vsync), then resync if more than one interval behind. Simulated against a jittered 60Hz stream: 15/20/24/30/45/50/60 now all hit their cap exactly, where before they gave 13.2/16.8/20/23.1/30/30/37.7.
- **`resetstat()` is what starts a race, and porting only its music half leaves the game with no beginning.** `starcnt = 130` and `gocnt = 3` (xtGraphics.java:1484) arm the intro fly-by and the 3-2-1-GO; `GameSparker.simulate` holds ALL physics while `starcnt != 0` and `stat()` draws the countdown and plays its four sounds on the way down. Both were fully ported and simply unreachable, so every test passed and the race just began instantly, mid-air. If a ported sequence never seems to run, check what arms it before re-reading the sequence itself.
- **`rd.setComposite` only reached the vertex colour, not the 2D overlay.** Java's AlphaComposite covers every drawing operation, so the countdown's NFM guy -- a `drawImage` under a 0.3 composite -- rendered as a solid opaque face. `graphics.js` now sets `text.globalAlpha` too, and `begin()` restores it to 1 so a composite left set by a throw cannot dim every later frame.
- **The countdown is silent unless something unlocks audio first.** It runs in the first ~7 seconds and both AudioContexts start suspended; the gesture that started the race happened on the launcher page and user activation does not survive navigation. `main.js` now unlocks on `pointerdown` as well as keydown/touchstart, so a click anywhere is enough.
- **`checkPoints.wasted` and `xt.cntwis` are recomputed every tick and cannot be forced.** `checkstat()` recounts `wasted` from the cars' `dest` flags, and `cntwis` is driven from `mad.cntdest`, so a test or a probe that assigns either gets one tick of effect at most. To end a race for real, set the loser's `dest` and let checkstat count it.
- ~~**The fps dips are fill-bound, not projection-bound (measured 2026-08-02, by ear/eye in a real browser).**~~ **Superseded 2026-08-09 — the res=1/res=2 discriminator no longer separates anything** (7.6 vs 7.8 ms/frame, MSAA off above 1x), so it can no longer be used to attribute a dip. Original follows. `?res=1` has noticeably fewer dips than `?res=2` on the same scene; projection cost is resolution-independent while fragment/fill cost scales with the backing store, so the dips track pixels. Consequence: **GPU-side projection would cut AVERAGE draw cost but not the dips.** The lever for those is overdraw (no depth buffer, so the painter's algorithm draws the whole scene) and the even-odd fill's area cost, which no counter tracks. Use the res=1/res=2 ratio as the discriminator before optimising anything in the draw path.

## 2026-08-02 — netplay determinism

- **Two browser tabs are two PRNGs; two worlds in one node process are one.** Any determinism test that builds both worlds in the same process is testing an interleaved shared stream that no real pair of clients has. Run the two ends in separate processes (`web/tools/netclient.mjs`) or sequentially with a re-seed between them.
- **The desync hunt only works field-by-field.** "The hashes differ at tick 835" is not debuggable; `car1.travxz is -53 here and 53 there at tick 102` is. `web/tools/netloop.mjs` reports the first differing FIELD, and every bug below was found by it in minutes. Include a hash of the collision MESH in that dump — mesh divergence showed up at tick 3 and did not reach the world hash until tick 1118.
- **Divergence sources found, all the same shape: presentation reading the SIM random stream, or a branch keyed on `im` instead of "is human".**

  - `crash`/`skid`/`scrape`/`gscrape` (sound) and `ContO.dust` (particles) likewise.
  - `Mad.drive` clears `control.wall` only for the local car and lets it persist for others; `wall` feeds `surfer` → `powerup` → `power`. Keyed on `im`, each client surfed a different car. Now `xt.human(i)`.

- **`XtGraphics.human(i)` vs `i === im`.** The Java has exactly one human, so it conflates "is this car the player's" with "is this car mine to draw and hear". Simulation branches need the first, presentation the second. Single player is unaffected: `human()` falls back to `i === im`, and the Java differential probe (`Mad.test.js`) still passes, which is what proves the rewrite did not change the game.
- **Lockstep needs the sender to simulate the value it TRANSMITS.** `steer` is analog and quantised to a signed byte on the wire; applying the raw float locally and the quantised one remotely desyncs with no packet ever lost.
- **Redundancy beats retransmission here.** Each packet carries the last 8 ticks of input (2 bytes each), so at 10% loss + 15% reorder 997/997 checkpoints agreed over 1000 ticks. At 30% loss it stalls often but still never desyncs.
- **A stale duplicate must never overwrite input already run.** An unordered channel delivers an older redundant copy after a newer one; applying it rewinds a tick the simulation has consumed.
- **A desync diagnostic can lie, and this one did.** Hashing a car's mesh over `plane.n` makes the hash a function of the CAMERA: `Plane.s()` sets `n` to 12 or 20 as a distance LOD, and each client has its own camera. So the game asked "is anyone looking at this car" and then changed the simulation: `fcnt` 7 or 8 makes `drive()` reset `hitmag`, `cntdest` and `dest`, which is how a wasted car re-enters the race. Two clients have two cameras, so the same car came back on different ticks on each. - **`fixit()`'s counter had the same shape:** `fcnt` was advanced at the end of `fixit()`, which `d()` only calls inside the on-screen test, so repairs progressed only while visible. Now `ContO.stepFix()`, called once per tick per car from `simulate()`.

## 2026-08-03 — the car editor, twice

- **Preserving every ported line let the applet dictate the UI, and that was the whole mistake.** The first shell ran the transpiled panes headlessly — the original's hit testing IS its drawing pass, so a pane can be run for its button rectangles and re-run with the mouse parked on one — and read their AWT widgets back into HTML. - **The rewrite is one rule: the `.rad` text is the model.** `rad.js` reads and rewrites the source directly; every control reads its value on load and writes it back on `input`; the preview re-parses with the game's own `ContO`. No Apply, because there is no second copy to apply anything to. - **Rewrite a directive IN PLACE, not by rebuild-and-append.** The applet's writers strip every `stat(` line and glue a fresh one onto the end. That is fine for a Save button pressed once and awful for a slider firing sixty times a second: the line you are dragging keeps jumping to the bottom of the textarea. Same for the wheels — and there, removing only the wheel LINES leaves the blank separator between the two axles behind, so every save grew the file by one line until the round trip was pinned by a test.

Tilting the model (`o.zy`) pitches it about its own axis, so which way "down" went depended on where the car was facing. Tilting the camera (`m.zy`) has the right axis — the renderer applies it last, after the yaw — but it rotates the world about a pivot at `(m.cx, m.cy, m.cz)`, 50 units in front of the lens, and a model 800 units away swings through an arc that is nearly vertical on screen. **Solve for the camera position that lands the model dead centre after both rotations** (`u = (D·cosφ·sinθ, D·sinφ, D·cosφ·cosθ)` from the pivot, using the engine's own `sin`/`cos` tables so it matches what the renderer computes) and it is an ordinary spherical camera: model at the origin, nothing translates. Verified by shooting pitch +70 and −40 and checking the car stays centred — not by asserting the angle changed, which is what hid it the first time.
- **The original game keeps the same numbers in two places, and only one of them is the `.rad`.** `CarDefine`'s constructor holds `handb[]`, `grip[]`, `lift[]`, `maxmag[]`… for the sixteen base cars, and `loadstat()` DERIVES those same tables from a custom car's `stat()`/`physics()` lines. So the sixteen ship with nothing in their `.rad` — which is why the Car Maker showed them blank, and why a car saved from one **never appeared in the launcher**: `loadstat()` sets `names[n] = ''` unless it finds both lines *and* a 16th `physics()` argument greater than zero, and `loadcar()` drops the slot. Not a launcher bug; a missing-data bug.
- **Invert a derivation by RUNNING it, not by re-deriving it.** `web/tools/embedstats.mjs` solves each `physics()` argument by calling `loadstat()` into a scratch slot and comparing the derived tables against the hand-authored ones. The slots that map one-to-one land exactly; the residual is printed. Two are unrecoverable in principle and the tool says so: `Pushes Others` is scaled by `(30 - lift) / 30` in INTEGER division, so any car with lift at all pins `push` to 2, and `airs`/`airc`/`powerloss` are three equations in two unknowns.
- **`loadbase()` checksums `models.zip` against a hardcoded uncompressed total**, so adding anything to a base model trips it (615671 → 621172 here). In this port that only logs a warning, but it also means **probe tests that build their input from live `models.zip` data silently change meaning when the data changes**: two `CarDefine` probes captured from real Java began failing because `formula7.rad` now carries its own trailing `stat()`, which overrides the header the test prepends. They strip the embedded block now. A test whose expectations came from an oracle must pin its INPUT too.

- **The "sometimes 2-4 fps" dips were the MACHINE, not the port — the CPU was pinned at its minimum 798MHz on a 2.9GHz part.** Proof takes one command and needs no browser: load all four cores for five seconds and watch `/proc/cpuinfo`; a healthy machine ramps, this one did not move off 798MHz. `intel_pstate` is in **passive** mode here (`status=passive`, driver `intel_cpufreq`), and in passive mode the `powersave` governor is the GENERIC cpufreq one, which always requests the minimum — it is not intel_pstate's load-aware active-mode algorithm of the same name. TLP sets `CPU_SCALING_GOVERNOR_ON_BAT=powersave` and sets nothing for AC, so one stint on battery pins the governor and returning to AC never restores it: hence intermittent, and hence "a reboot sometimes fixes it". - **`?musicvol=0` does NOT stop the music mixer costing CPU.** BassoonTracker mixes in a `ScriptProcessorNode` — main thread, 256 samples a callback, ~5.8ms — and the volume is a gain node downstream of all of it. Silencing it changes nothing about the cost. `?music=0` (and now `musicvol=0`) calls `music.disable()`, which refuses to init at all; that is the only usable A/B against a frame-rate problem.

- **A killed chromium leaves its profile lock behind, and the next launch then hands the URL to the dead session** ("Opening in existing browser session") and never opens a debugging port. Same "no devtools target" symptom, different cause. Use a per-run `--user-data-dir`. And do not clean up with `pkill -f <pattern>` where the pattern appears in the killing command's own line — `pgrep -f` matches the shell running it, so the pipeline kills itself and reports exit 144.
- **fps averages cannot describe an intermittent stall, and `?bench=` reports the mean of two different machines.** `?spike=<ms>` logs every frame whose rAF gap exceeded the threshold, split into sim / draw / gl / other / **OUT** (the gap minus our own callback — GC, the audio mixer, compositing). ## 2026-08-05 — netplay: lockstep -> client-authoritative state sync

- **Node 18 is why 31 tests "failed" here, and none of them were about what they said.** `DecompressionStream('deflate-raw')` landed in Node 20, so every zip-dependent test died in `vfs.js`'s `inflate` and reported as a CarDefine/loadbase/sounds/models failure. Same family as the missing-global-`WebSocket` entry above. Node 22 takes the suite from 269/300 to 303/304 with no source change; the one remaining failure is `carstore.test.js` reading `mycars/custom_formula7.rad`, which `.gitignore` hides, so it only passes on a machine that has run the editor.
- **The state-sync field set is real game logic and is now pinned against the Java by a test that PARSES `UDPMistro.java`.** 16 booleans (`setinfo`'s 15 plus `holdit`, which is why `readinfo` asserts a 16-character string) and 20 numbers. A round-trip test cannot catch a wrong field list — it is symmetric and agrees with any self-consistent mistake — so `netcodec.test.js` extracts `setinfo`'s append chain with a balanced-paren scan and diffs it against `NUMS`. A regex cannot do it: the arguments contain nested parens (`(int)(mad.speed * 100.0f)`) and a lazy match stops at the first `)`.
- **Damage crosses the wire as a PERCENTAGE of the sender's own ceiling**, and `readinfo` multiplies it back by the RECEIVER's `maxmag[cn]`. Two players in different cars therefore exchange `magperc`, not `hitmag`. Transmitting the absolute would be the obvious port and would show the wrong damage bar on every mixed-car race.
- **Comparing two state-sync clients at the same tick index is the obvious measurement and it is wrong.** It reports (latency x speed) — 250-500 units at race pace — and reads as a catastrophic desync when nothing is wrong at all. The number halves when latency goes to 0, which is the tell. Measure instead by finding the tick offset that best ALIGNS the two clients and reporting the residual there: the guest's view of a host-owned car trails by exactly LATENCY ticks with a residual of 0.0-4.8 units on a clean channel. Offset = truth about the pipeline, residual = truth about the reckoning.
- **The worst single correction must NOT be a pass/fail gate.** It reaches ~600 units at 30% loss because a run of lost packets lets the prediction wander before it snaps back — the price of the loss, not a protocol defect, and the fix is render-side smoothing. Gating on it fails healthy runs. `netloop.mjs` gates on steady-state residual and on drift GROWTH (second half vs first) instead, and reports the worst correction as the smoothing budget.
- **Drift that stays flat or shrinks across a run is the health signal.** At 0/10/30% loss the first-half-to-second-half ratio is x0.52 / x0.97 / x0.72 — dead reckoning converging, not separating. A ratio above ~1.5 would mean the two worlds are drifting apart in a way no packet rate fixes.
- **A guest must not run the AI for the host's bots.** `Control.preform()` was already skipped for `human` slots; state sync needs it skipped for every car the client is not AUTHORITATIVE for, which on a guest includes the bots (`GameSparker.java:1348` runs `preform()` for bots only when `im == 0`). Added `Control.remote` alongside `human`. The guest still runs `drive()` for them — that IS the dead reckoning — but must not re-decide their intent.
- **State sync deletes the local-input shadow control that lockstep needed.** Lockstep overwrote the live `Control` every tick with input agreed `delay` ticks earlier, which undid key releases (car accelerates forever), hence `pad`. Under state sync a client is authoritative for its own car, applies input the instant it happens, and only ever overwrites cars it does not own — so the keyboard drives the live Control directly and local input latency is zero.
- **Lockstep's sync-checker bug cannot recur under state sync, structurally.** The old `netCheck()` read the peer's hash for the tick it was ON, which was still in flight, so it compared nothing and reported success. Drift here is measured against a packet that has by definition already arrived, so there is nothing to wait for. Worth knowing it is gone for a reason and not by care.
- **The parent must keep stepping clients past the target tick.** `netloop.mjs`'s clients only report `done` when ASKED to step and finding they have arrived; a parent that stops sending steps at TICKS leaves both idle waiting for each other. The deadlock looks exactly like a protocol stall from the outside, which is the wrong place to go looking.
- **Headless browser tools play sound out of the real speakers.** `--autoplay-policy=no-user-gesture-required` is needed to exercise the audio-unlock path, and without `--mute-audio` alongside it `browsern.mjs` plays the engine loop and the soundtrack aloud — twice, one per browser — for the length of the run. Both it and `spike.mjs` now pass `--mute-audio`, which nulls the output sink while the Web Audio graph (and so the ScriptProcessorNode's main-thread cost) still renders.
- **"Host-authoritative" was the wrong name for this topology and it misleads about the trust model.** The host does not simulate other players' cars and arbitrates nothing; each client simulates its own car and transmits the result as fact, with the host owning only the bots (which have no client to speak for them). So it is CLIENT-authoritative, every client is trusted to be honest about itself, and there is no validation anywhere — a modified client can declare itself anywhere on the track. Deliberate for a private no-backend game; if anti-cheat is ever wanted it means real host authority (guests send INPUTS, host simulates everything) and a round trip of input lag for everyone but the host.

## 2026-08-05 — netplay: three or more players

- **The star beats a mesh here because state packets are absolute.** One connection per guest, host relays; a relayed copy of an absolute-state packet is worth exactly as much as a direct one, so the mesh's N(N-1)/2 connections and N-1 uploads per guest buy nothing. Guest upload stays flat at one car regardless of player count and only the host's scales. Lockstep could not have used this shape — it needs every peer's INPUT before it may step, so a relay would have added the host's latency to every gate.
- **Relay guests' packets VERBATIM; do not re-capture those cars from the host's world.** Re-capturing makes the host authoritative for a guest's own car, which costs that guest a round trip of input lag on the car it is steering — the exact thing this topology exists to avoid. Forwarding raw bytes also keeps the originating client's slot and tick, so the per-slot staleness rule needs no special case.
- **Slot assignment must be the host's alone.** Two guests choosing their own slot can pick the same one, and nothing downstream notices: they simply drive the same car, on every screen, and the first symptom is a car that steers like two people are holding it.
- **A host that awaits one connection at a time strands players.** PeerJS fires `connection` whenever it likes, so a guest can complete its handshake while the host is still awaiting an earlier one. Register the `connection` handler ONCE for the session and queue arrivals (`netpeer.js` `pending`/`waiters`); a per-guest `await` on the event drops anyone who arrives early.
- **Model BOTH hops when simulating a relay.** A harness that delivers guest-to-guest in one hop understates the lag dead reckoning must cover and reports a tracking quality no real session reaches. With both hops modelled the measurement is unambiguous: 1-hop views trail exactly LATENCY ticks, relayed views exactly 2xLATENCY, which is also the cheapest confirmation that the relay is wired the way you think.
- **Two players cannot test the path that matters most at three.** Guest-to-guest is the only traffic that is relayed rather than sent directly, so every two-player test passes with the relay entirely absent. `netloop.mjs` now compares every car against every NON-OWNER, and `browsern.mjs` asserts each client heard every other player by slot — the drift line carries `slots=` for exactly this reason, since a guest hearing the host but not the other guests is indistinguishable from health in a bare drift figure.
- **This machine cannot measure drift with three browsers open.** Headless SwiftShader, no GPU, three copies of the game: tick rates spread 7.4–19.4/s, and a client running at a third of another's rate sends state three times too slowly, producing 700–1800-unit corrections that say nothing about the protocol. `res=1&interp=0&overlay=0` was not enough. `browsern.mjs` therefore gates on pairing and reachability and only REPORTS drift; `netloop.mjs`, which controls pacing exactly, is where drift is measured.
- **`netstate.js` split into `netcodec.js` (wire format) and `netsession.js` (ownership, staleness, drift).** The seam is reason-to-change: the codec is a transcription of `UDPMistro.setinfo`/`readinfo` and moves only when the Java does, while the session follows the topology. `encodePacket`/`decodePacket` are free functions rather than `StateSync` methods, since serialising never needed to know who owns what. `netfixture.js` holds the shared `fakeCar` so the two test files cannot drift apart.
- **Lobby and chat get a SECOND DataChannel, reliable and ordered, over the same peer connection.** `peer.connect(id, {label, reliable})` twice reuses the existing ICE/DTLS session, so the second channel costs a channel and not another negotiation. State stays unreliable/unordered because absolute state is self-superseding; nothing else is — dropping a chat line or a `start` message does not heal itself. This also fixed a live bug: the join handshake was riding the UNRELIABLE channel, so a dropped `hello` or `start` stranded the guest at "connecting" forever with nothing to retry.
- **Pair a guest's two channels by `conn.peer`, never by arrival order.** Two channels per guest arrive as two independent `connection` events and interleave when several guests join at once, so ordinal pairing eventually hands one player's state channel to another player's chat. `accept()` resolves only once BOTH halves are open, because the handshake that follows it goes out over the reliable one.
- **A bare `sendMessage` already reaches every connection**, which for the host is every guest and for a guest is the host (who relays onward), so adding a host-side relay branch on the SEND path double-sends the host's own chat lines. The relay belongs only on the RECEIVE path.

## 2026-08-06 — netplay: PeerJS -> p2pt

- **PeerJS cannot list anything, and that is why the transport was swapped.** The public broker's discovery endpoint is gone (`GET https://0.peerjs.com/peerjs/peers` -> 404; `allow_discovery` is off), so a peer id can only be RESOLVED, never learned. A game browser on PeerJS therefore needs either a hardcoded id squatted by one player's browser tab (a directory that dies with that tab, and that anyone can forge) or a registry of our own. p2pt announces on public WebTorrent trackers under an IDENTIFIER and is handed everyone else announcing the same one — the rendezvous PeerJS structurally lacks. A room is an identifier; a future game browser is one well-known identifier every idle client announces on.
- **Reliable+ordered costs nothing at realistic loss, and that is what made the swap affordable.** p2pt is built on simple-peer's default DataChannel, so the unreliable/unordered state channel is not available. Measured by adding a `reliable` mode to `netloop.mjs` (a lost packet is retransmitted a round trip later and everything behind it on that link waits — real head-of-line blocking), steady-state residual unreliable -> reliable: **0% loss 22 -> 3 units, 2% loss 46 -> 9, 10% loss 24 -> 101, 30% loss 40 -> 354** (limit 400). Reliable WINS below ~2% because retransmission costs less than the unordered channel's reordering. It degrades above 10%, where stalls reach 11-19 ticks (0.6-1.0s of frozen car) — and that is NOT what render-side smoothing fixes: smoothing hides a transient snap, not a persistent 100-350 unit offset. Repro: `node web/tools/netloop.mjs 800 <loss> 2 15 2 reliable`.
- **The retransmit model is a plain RTT-timer geometric retry, no fast-retransmit and no SACK,** so real SCTP does somewhat better at low loss and about the same at high. Single runs on one fixed noise seed. Good enough to decide a transport; not a number to quote.
- **p2pt makes the topology a MESH, and the star's relay had to be deleted, not kept.** Every peer on an identifier discovers every other, so a guest sends its own car straight to the other guests — 1 hop instead of 2, and guest-to-guest lag halves. Keeping the host's relay alongside would deliver every packet twice; `StateSync.accepts()` refuses the duplicate on the tick rule, so it would have been invisible rather than broken, which is worse.
- **"The first peer I meet is the host" is false on a mesh, and it deadlocks the handshake.** A third player can complete ICE with guest 1 before the host, so a `hello` addressed to "my first peer" goes to another guest, which ignores it, and both ends wait forever. Verified in three browsers: all peers paired, all reported `connected to 2 peer(s)`, and the race never started. The guest now greets EVERYONE and re-greets each late arrival; the host is whoever answers with `start`. There is no transport-level notion of host and there should not be — it is a role in the handshake.
- **A `hello` can arrive before the host has accepted that connection.** p2pt opens the channel and the guest greets immediately, while the host is still awaiting an earlier guest, so a per-connection `await` dropped it. Buffer greetings in a Map and have the waiter check the buffer first. Same shape as the PeerJS-era "register the connection handler once and queue arrivals" entry — the accept path attracts this bug.
- **Do not send game traffic through `p2pt.send()`.** It wraps every message in its own JSON envelope with a chunking header and registers a response resolver in `responseWaiting` that nothing ever resolves — a leak per message — and it is far too heavy for a per-tick binary packet. `netpeer.js` uses p2pt only for discovery and connection, then frames its own bytes on the raw simple-peer channel: first byte `0x02` = state, `0x03` = JSON lobby/chat. p2pt's own frames start with `^` (0x5E) and are ignored, so the layers cannot collide. Cost: no chunking, so lobby messages must stay under the 16KB DataChannel limit.
- **Three public trackers answer from this machine (2026-08-06):** `tracker.openwebtorrent.com`, `tracker.webtorrent.dev`, `tracker.btorrent.xyz`. `novage`, `sloppyta` and `files.fm` refuse or time out; several are listed anyway because p2pt announces on all of them and dedupes the peers, so losing one costs nothing. Check reachability before blaming the handshake — a tracker list that has rotted looks exactly like a room that does not exist.
- **The vendored p2pt ESM dist is 86 KB raw / 21.9 KB gzipped, SMALLER than the PeerJS bundle it replaced (25.5 KB gz)**, and it is a real ES module with a guarded `globalThis`, so it imports cleanly. Still loaded via a lazy dynamic import, per the `bassoonplayer.js` lesson.

## 2026-08-06 — the launcher, wired to the netcode

- **`frame(tag, payload)` JSON-stringified every state packet, and everything still LOOKED fine.** A `Uint8Array` is `typeof 'object'`, so a `typeof payload === 'object'` test written before the binary check turned each packet into `{"0":12,"1":88,...}`. It framed, sent, arrived and parsed as a frame; only `decodePacket` returned null, so both clients raced on dead reckoning forever while the lobby, the chat and the roster worked perfectly. **Check `ArrayBuffer.isView` FIRST in anything that branches on payload type.**
- **A drift report is not evidence that anything was heard.** `main.js` logs `drift @N` on a timer whether or not a packet arrived, so the first version of `browserlobby.mjs` gated on "more than zero drift reports" and passed while both clients heard nothing at all — it is what hid the stringified packets above. Gate on the SLOTS in the line (`heard slots [1]`), which are only populated by `markApplied`. Same family as lockstep's checker that compared nothing and reported success.
- **A row clicked just after its list re-rendered did nothing.** The games list rebuilds by `innerHTML` every few seconds as the directory hears from hosts, so the clicked element is a different object from the one in the cached `items` array and `indexOf` returned -1. The handler now re-indexes the page before giving up. Any list that repaints on a timer has this bug available to it; keyboard navigation never hits it because it works off the index.
- **Joining a room is a SECOND tracker rendezvous and can take over a minute.** The directory finds the host on the `nfm-directory-v1` identifier, but the room is its own identifier and has to be discovered from scratch, so "I can see the game" and "I can join the game" are seconds to minutes apart. Most joins are a few seconds; the outliers are the trackers gossiping, not the code. Consequences: connection status has to be STICKY (a toast that fades after 2s leaves the player looking at an unchanged screen for ten), and any test needs ~2 minutes of patience before calling a join broken.
- **The lobby forced the launcher and the game into one page, and `boot()` had to become a function of its inputs to allow it.** A navigation tears down the RTCPeerConnection, and the lobby must run BEFORE the world exists (the host ships seed/stage/grid verbatim, because `sortcars()` consumes randoms). So `boot({ params, session, onExit })`: `main.html` passes nothing and reads the query string, the launcher passes menu settings plus the live `{net, cfg}` its lobby negotiated. Nothing runs on import any more — a module that raced on import could not be imported by a page that is not ready to race.
- **The race ends by RELOADING the launcher, deliberately.** `boot()` installs input listeners, an rAF loop, an audio graph and a music mixer; unwinding all of that by hand to reach a menu that rebuilds from localStorage in a few hundred milliseconds would be a lot of teardown nobody would ever exercise.
- **One lobby protocol, two drivers.** `netlobby.js` holds the handshake; the launcher drives it from a screen where a person presses Start, and `main.js`'s `?net=host&humans=N` drives the same object with `autoStart`, which is what `browsern.mjs` tests. Writing the handshake twice would have let the tested path and the shipped path drift apart.
- **The host is the only writer of the roster.** Guests render what they were last sent and never merge their own view, which is the same rule slot assignment follows and for the same reason: two clients each maintaining a roster eventually disagree about who is in slot 2, and nothing downstream notices until both drive the same car.
- **The game directory is one well-known identifier (`nfm-directory-v1`) that idle clients announce on.** No registry, no authority, no persistence: the list is exactly the set of hosts holding the Multiplayer screen open. Entries carry an arrival time and EXPIRE (16s, re-announced every 5s) because a host that closes its laptop cannot withdraw, and a peer that disconnects has its games dropped at once so the list feels live. Ping is a round trip on the directory channel, not on the room's.
- **The slab backdrop is CSS now and the rAF loop is gone.** A `repeating-linear-gradient` on a strip that overhangs by more than one period, translated exactly one period, is compositor-only and pixel-equivalent to the canvas version the mockup painted at 20fps. This is the change TASKS.md asked for, and it takes the launcher's steady-state cost to zero.

## 2026-08-06 — one swarm, and why joining took 30 seconds

- **p2pt's `setIdentifier()` is async and unawaited, and the SECOND swarm in a page announces with no `info_hash`.** The constructor calls it without awaiting; `start()` awaits `this.infoHash` (the hash promise) rather than the method, so `_infoHashBinary` — which the announce actually reads — is assigned one microtask too late. It survives whenever the websocket has to be dialled first, because the announce is deferred to the socket's `connect`; it fails whenever the socket is already open, and **bittorrent-tracker pools sockets per tracker URL across every p2pt in the page.** Upstream bug, ~2 lines to fix there; `makeP2PT()` awaits the identifier and is kept even though only one swarm exists now.
- **A tracker reply with no `action` field DESTROYS the tracker for 10s–5min, and we were logging it as harmless noise.** The malformed announce above draws `{"failure reason":"Invalid request"}`, which has no `action`, and `_onSocketData` treats an unrecognised action as a socket ERROR: `destroy()` plus `_startReconnectTimer` (10s + up to 300s of jitter). The socket being shared, it takes every swarm in the page down together. **This is what "invalid action in WS response: undefined" was** — the warning we saw, diagnosed as a tracker answering badly, and routed to `console.warn`. Measured: room rendezvous 10–40s or never, against ~300ms once the hash is awaited.
- **WebTorrent trackers are NOT strictly request/response.** An earlier note here implied a peer only learns about others when it announces. Wrong: the socket is long-lived and the tracker PUSHES a newcomer's offers to everyone already in the swarm, measured at ~120ms from announce to arrival. So sitting still is enough to be found, and `Directory`'s `requestMorePeers()` every 5s was fighting a symptom of the bug above rather than a real gap. It is deleted; it also spun up 5 `RTCPeerConnection`s per tracker per call (`trickle: false`, held 50s), so ~150 could be live at once.
- **A room does not need to be a tracker identifier, and making it one was the whole cost.** By the time you click a game in the list you are ALREADY connected to that host over the shared swarm; the old join threw that connection away and paid a second full rendezvous to rebuild the identical link under another name. Now there is one identifier (`nfm-v1`), frames carry `[tag][len][room]`, and joining a listed game is a message. **Measured end to end (`browserlobby.mjs`): join 31.5s -> 0.6s, and hosting is local.**
- **On one swarm, membership has to be conferred rather than observed.** Everyone on the swarm looks alike, so the host publishes each player's peer id in the roster and guests adopt that as the room's membership — which is also what lets guest-to-guest state stay direct. The old "greet everyone and the host is whoever answers" disappears with it: `join()` seats the peer that advertised the room, so the host is member 0 by construction and the greeting is addressed.
- **`Mesh.lock()` is what stops the swarm being unbounded.** At race start we stop announcing (`tracker.setInterval(0)` clears the timer without setting one) and destroy every peer outside the room, so a racing client holds exactly its players. Measured with 2–3 peers only; the mesh cost at 20 is unknown and is the thing to watch before this design is trusted at scale.
- **`web/tools/browserlobby.mjs 5` is too short to prove state flows.** The drift line prints every few seconds, so a 5s race can end with zero reports and fail a check that is really about the race being long enough. Use 15s.

## 2026-08-06 — the multiplayer race lifecycle

- **A netplay race was running at `fase = 0`, so the game believed it was single player.** Every multiplayer branch of `stat()` keys on `fase === 7001` and `lan`, and all of them were dead: the wasted announcer read out CAR names instead of `plnames` (`XtGraphics:1737`), a wasted player fell through to "Press [Enter] to continue" and was dropped back to the launcher instead of taking `exitm = 4` and spectating (`:1106`), the hold length was the single-player 250 instead of 600/1200, and "(Disconnected)" was unreachable. `main.js` now sets both. **Two separately-reported bugs, one line of cause** — when a transcribed branch "isn't working", check the mode flags before reading the branch.
- ~~**DELIBERATE DEVIATION at `XtGraphics:936`.**~~ **Reverted, along with two others — do not re-add them.** Three edits were made INSIDE the transcription to paper over unported multiplayer branches, and all three are backed out so the lifecycle port starts from an unmodified `XtGraphics`/`Mad`: (1) dropping the `im != 0` term at `:936`, which in the Java ejects a wasted GUEST after 1200 ticks while the host spectates indefinitely; (2) a `colme` per-car timer to attribute kills; (3) Escape-to-leave, which is our-side and is KEPT for now, marked INTERIM, because without it a networked race cannot be left at all. **The lesson is the pattern, not the edits:** every bug found by playing was an unported branch, each was patched one bug report at a time, and the third round of that is more expensive than porting the block. See TASKS.md, "Port the multiplayer race lifecycle".
- **`Mad.lastcolido` cannot attribute a kill once more than one person is racing.** It is set by a collision with ANY human (`if (xt.human(im))`), so `dested == 2` means "somebody hit them recently" and every client read it as "*I* wasted them" — reported as "You wasted Player 2" when the AI did it. The original does not solve this locally either; it carries attribution over the wire and prints `plnames[im] wasted plnames[n9]` on the `multion >= 2` path. Port that rather than inventing a local timer.
- **On one swarm, leaving is no longer a disconnect.** The peer connection outlives the lobby and the race — that is the point of the design — so `peerclose` never fires when somebody quits, and departures have to be SAID: `{t:'bye'}` in the lobby (`Lobby.leave`) and in the race (`leaveRace`). The old room-per-swarm design got this for free, which is exactly why it is easy to miss when changing the transport.
- **A disconnected car has to become a game event or the race cannot end.** A car nobody transmits dead-reckons forever, never becomes `dest`, and "everyone else is wasted" is then unsatisfiable. `playerGone()` wastes it locally and sets `checkPoints.dested = 3`, which is the original's own disconnect marker (`Mad:1812` preserves a 3 where it clears a 1 or 2) and what makes `stat()` announce it as a disconnect. **It must waste everything that player OWNED, not just their own car** — the host owns the bots, so a host leaving otherwise strands one uncrashable car per bot and every survivor sits in a race that can never finish. There is no host migration to hand them to.
- **A goodbye can lose a race with the page reload.** `send()` only queues into the DataChannel, so `leaveRace()`'s `{t:'bye'}` could still be in the buffer when the reload tore the connection down — putting the others back in exactly the state the message exists to prevent. `NetPeer.flush()` waits on `bufferedAmount`, bounded at 250ms.
- **`Lobby` had no disconnect handling at all** — `NetPeer.onClose` was assigned by nobody. A guest that closed its tab stayed on the roster, kept inflating the advertised player count, and was seated into the race as a car with no driver.
- **The lobby's start message is the decision to race, not the moment to race.** Each client then loads its own stage, HUD images and sounds — seconds, and different per machine — so whoever finished first ran the 3-2-1 alone and raced into a car that was still parsing zips. `waitForEveryone()` barriers on a `ready` broadcast, re-sent on a timer because a `ready` that arrives while the other client is still in `boot()` reaches the LOBBY's message handler, which drops what it does not recognise. It times out and races rather than stranding everyone on one broken load.
- **At fase 7001 there is no way out of a race**, because the `fase == 0` quit branch is skipped in favour of `exitm`'s confirm menu — which lives in `multistat()`, is mouse-driven, and is part of the unported menus. Escape sets `fase = -2` directly (the Java's own leave signal) as an INTERIM stand-in until `multistat()` is ported. It fires while `holdit` is up too, and must: a wasted player is SPECTATING there with `exitm == 4` swallowing Enter until the race ends, which is the exact moment somebody wants out — an earlier version excluded `holdit` and left spectators with no way to leave at all.
- **`pos` was transmitted and thrown away.** `netcodec`'s comment said it was applied; `applyCar` writes it back onto the record and `main.js` passed no sink, so the remote leaderboard only corrected itself when `checkstat` recomputed. A claim in a comment is not a wiring.
- **Rematch survives the reload as data.** The race still ends by reloading the launcher (unwinding `boot()`'s listeners, rAF loop, audio graph and music mixer by hand is teardown nobody would exercise), so the room goes into `sessionStorage` and `resumeRoom()` re-enters it: the host reopens the SAME code, guests re-`find` it. Cheap only because a join is now a message — `#find` retries every 2s because both sides are reloading and whoever returns first asks into an empty swarm.

## 2026-08-09 — where the frame rate actually goes

- **`Record.rec` is ~74% of everything the game allocates, and it is the replay's ghost buffer.** `Record.rec` copy-constructs a whole `ContO` six times a cycle per car, and a `ContO` copy clones one `Plane` per face with several typed arrays inside each: heap-profiler attribution is `Plane@Plane.js:22 <- #initCopy@ContO.js:831 <- ContO@ContO.js:39 <- rec@Record.js:246` at 57.1 + 9.3 + 6.5 + 0.8 + 0.6%. ~5MB/s, heap 57 -> 156MB across a race, then one frame frees **110.9MB**. Nothing in the port reads the buffer back — the replay viewer is in the unported xtGraphics menus — so it was pure cost. `Record.ghosts` (launcher "Replay recording", `?ghost=0`) turns it off; the heap then oscillates flat at 110-115MB.
- ~~**The symptom of that allocation is a whole SECOND at 17fps ... everything inflates together ... V8 charges incremental marking to whatever code is running.**~~ **Wrong diagnosis, superseded by the catch-up-draw entry at the end of this section.** Sim, backdrop, shadow and object loop really did inflate together on the same scene counters — but because the frame was DRAWING the scene two to four times, not because of GC. The observation was sound and the explanation was invented to fit it. The half worth keeping: **when a slow frame's scene counters are no worse than a fast frame's, something is repeating work the counters only measure once.**
- **`Plane.s()` is the ground SHADOW, run for every plane of an object** — ~5,000 calls/frame with the car pack in view, 20-60ms of a 200-330ms draw against 1.0-2.4ms when the camera looks away. (Both the call count and the ms here are per FRAME and predate the catch-up-draw fix, so they cover two to four draws of the scene; per draw they are correspondingly smaller.) This is why turning away from the other cars restores 60fps. Nothing counts it: a shadowed face submits its vertices like any other, so no scene counter can distinguish a frame with seven shadowed cars from a frame with none. (`Plane.s` is NOT the damage animation; that reading of it in the 2026-08-01 notes is wrong.)
- **With `interp=0` the target is unreachable by construction** — the game draws only on a tick, so fps is pinned at 18.9 and no optimisation can raise it. A "tanked fps" report in that mode means dropping BELOW 18.9. Only `interp=1` can be asked for 30+.
- **The spike line now carries the scene counters, latched from the frame the timings describe.** Reading `rd.*` at print time reports the NEXT frame's scene against the previous frame's cost. It also carries `heap`/`dHeap`, and under `?prof=1` the backdrop, the car-rebuild and the shadow slices.
- **`web/tools/profile.mjs` is the CPU + allocation sampler.** `spike.mjs` can only say which BUCKET a long frame went to, and the answer is always "draw"; this gives a function name, and the heap half gives the allocating call path (keyed by two ancestors, because `new Plane` as a leaf tells you nothing).
- **`--js-flags=--trace-gc` crashes this chromium** (`*** stack smashing detected ***`, and the tab has to be killed by hand). Use `performance.memory` with `--enable-precise-memory-info` instead — a spike frame that shows the heap DROPPING was a collection, one that shows it merely growing did the work it was charged for.
- **Holding accelerate is NOT a representative benchmark, and it invalidated a whole afternoon of "steady state" figures.** The player's car is shunted off the grid and spun 180 degrees within seconds, so the other cars — which are most of the scene and all of the shadow cost — spend the run off screen. That is what made stage 1 look like a flat 60fps with spikes "only in the first 15s". Parked at the grid with the pack in view (`NFM_KEY=none` in `spike.mjs`) the same stage is **39-45fps**, stage 5 is 34-41, and **stage 9 is 14-23**, with spikes throughout. Measure with the pack on screen or the number means nothing.
- **`?ghost=0` is worth keeping and is NOT the frame-rate answer.** In the representative condition it flattens the heap (129MB steady against 191 and climbing) and removes the whole-second stalls, and leaves fps and the frame-gap tail untouched (39-41fps either way; 100ms+ buckets 38/23/7/1 against 32/24/8/0). An allocation fix and a draw-cost fix are different problems.
- **Where a representative frame goes (stage 9, parked, res=1, interp=1, ghost=0):** `Plane.d` 25.1%, `ContO.d` 21.2%, `scratchInt` 8.9%, `_fillTrapezoid` 7.6%, `Plane.s` (shadow) 3.6%, `fillPolygon` 2.5%, `rot` 2.4%, GC 2.3%, `intArray` 2.2%. So projection and traversal are ~59% of the frame and the fill ~11% — which restores the 81/19 split TASKS.md already had. No idle time at all in this profile; the CPU is saturated. (This entry originally concluded that GPU-side projection was therefore the right lever. It is not — see the shader entry below, written after reading `Plane.d` rather than the profile.)
- **Array pooling is still a pessimisation, now confirmed in a browser on a representative scene** (stage 9, parked): `?pool=1` renders 323 frames in 25s against 419 with pooling off, and moves the distribution the wrong way (50-100ms bucket 77 against 41). The node-only measurement in the 2026-08-01 entry was right, for once, despite having been taken on a scene that was not representative.
- **Check whether the laptop is on BATTERY before believing a run, not just the governor.** A verification run mid-session reported 1-24fps and a 21,436-vertex scene that never moved; it was a battery stint, and TLP's `CPU_SCALING_GOVERNOR_ON_BAT` is the trap already documented above. `spike.mjs` prints the CPU ceiling and mean MHz for exactly this reason — read those lines first.
- **A vertex shader cannot take `Plane.d`'s transform without replacing the game's culling and shading model.** Culling, `av`, the `b4`/`lastmaf` orientation flags (which are CROSS-FACE state — `m.lastmaf` decides whether a later face mirrors its own geometry) and the brightness that becomes the vertex colour all read the transformed coordinates before anything is submitted, and the even-odd fill needs screen space regardless. TASKS.md's note that the depth sort does not block this is true and beside the point. Full reasoning is in the `[!]` entry above the GPU-projection task.
- **`rot` is 2.4% of a representative frame and `Plane.d`'s own body is 25.1%,** so the per-vertex rotation a shader would take over is not where the time goes. Whatever is expensive in `d()` is in the branchy per-face work, not the vertex loop.
- **The O(n^2) vertex-pair sweep in `Plane.d` costs nothing measurable.** It looked like the obvious culprit — 400 iterations per 20-vertex face, ~1.27M a frame at stage 9, computed before the cull and discarded when the face is culled — and stubbing it out moved the frame count from 391 to 399 over 25s, i.e. noise. Written down because the reasoning was persuasive and wrong, and the five-line stub that refuted it cost minutes where the "obvious" reorder would have cost an afternoon.
- **V8's `positionTicks` gives LINE-level attribution inside one hot function, and it replaces a day of stubbing.** `NFM_LINES=ContO.js:1194 node web/tools/profile.mjs` prints ticks per source line for the function starting at that line. One run found what eight A/B stub runs would have: `ContO.d`'s O(npl^2) face sort is 58.6% of that method. (Watch out that `URL` is shadowed by the page-URL constant in `profile.mjs`.)
- **The per-object FACE sort was ~12% of the whole frame, and it is a rank count in the Java.** `ContO.d` ordered an object's faces back-to-front by comparing every PAIR — ~5,000 comparisons a frame for a 100-face car — and it computes exactly a stable descending sort by `av`: a face's rank is the number of faces with greater `av` plus the number of equal-`av` faces with a lower index, since the inner loop starts at `n11 + 1` and every tie increments the later index. Replaced with `Array#sort` (stable by spec since ES2019). **Measured, stage 9 parked: 406 -> 528 frames in 25s (+30%), frames under 20ms 28 -> 134; stage 1: 717 -> 778 (+8.5%), under 20ms 307 -> 405.** `?facesort=rank` restores the original.
- **An equivalence proved on paper is not an equivalence, when the ordering IS the depth buffer.** The face-sort test draws a real 40-tick scene both ways and compares every vertex word, rather than asserting the rank arithmetic — a subtly wrong tie rule would still produce a plausible screenshot, which is the failure mode the whole no-depth-buffer design is prone to.
- **`Plane.d` has no single hot block and never will.** Line-level ticks spread across the initial vertex copy 13.4%, the O(n^2) vertex-pair sweep 12.3%, the O(n^2) screen-extent sweep 10.7%, the two projection loops ~12%, colour and fog ~5%. Each is 2-3% of a frame, so stubbing them one at a time returns noise every time — which is exactly what the `pairskip` A/B showed. The lever for `Plane.d` is calling it FEWER times, not making it cheaper.
- **The tanked frames were the frame loop DRAWING ONCE PER CATCH-UP TICK, and it is a spiral rather than plain waste.** A late frame earns several ticks, `main.js`'s `while (acc >= TICK_MS)` loop ran a full `gs.draw()` on each, and every one of those batches except the last is thrown away — by `rd.begin()` on the next iteration, or by the interpolated redraw. So the next frame is later still. Now only the LAST tick of the loop draws; the others call `rebuildNewCars` directly, which is the simulation part of `draw()` (same reason `?draw=0` does). **Measured, parked: frames over 100ms stage 9 17 -> 4, stage 1 9 -> 2, nothing over 200ms on either, and total frames +5.5%.** `?catchupdraw=1` restores the old behaviour.
- **The counter that found it was Plane.d CALLS per frame, and no existing counter could have.** `rd.faceCalls` is reset by `rd.begin()`, so a frame drawing four times reported one draw's worth of faces; the spike line showed `face=4087` next to `planeD=187.6ms/16348` — exactly 4x — only once `main.js` counted calls across the whole frame instead. Any counter reset per BATCH is blind to a frame that makes several batches.
- **Profile the tanked frames, not the run.** `NFM_SPIKES=100 node web/tools/profile.mjs` splits the samples by whether they landed inside a frame the page logged as a spike, anchoring V8's `profile.startTime` to one `performance.now()` reading taken at `Profiler.start`. It prints sampled-time-inside-windows against the gap budget as a self-check; ~70% is right (the rest is off-thread), and a wild mismatch means the clocks did not line up and the split is meaningless. Whole-window percentages describe the hundreds of ordinary frames and hid this completely.
- **`?draw=0` is the fastest way to prove a stall is in the renderer.** Same scene, same physics, no drawing: 1,424 frames in 25s with ZERO spikes, against 30+ spikes with drawing on. It does not discriminate between draw's work and the GC pressure draw's allocation causes — both vanish together — but it rules out the machine, the audio thread and the simulation in one run.
- **Array pooling is DELETED, after being measured as a pessimisation twice.** The rewrite to a direct property (no Map, no `slot + ':' + n` key) is STILL slower: stage 9 445 frames against 514, stage 1 neutral. The 30% pessimisation was never about the Map. A small `Int32Array` dies in V8's young generation without ever being scavenged, while a reused one is promoted to old space and pays write barriers. `scratchInt` showing 10.1% of a frame is not 10% that can be recovered. So `scratchInt`, `setPooling`, `isPooling`, `?pool=` and the two pooling equivalence tests are gone and `Plane.d` allocates directly; a flag nothing should ever turn on is not worth a branch in the hottest function in the port. Confirmed no regression after removal: stage 9 557 frames with 3 over 100ms, the best figure measured.
- **Interpolation was drawing the whole scene TWICE on every frame that ran a tick, for one picture.** The tick drew, `simulate()` ran, then the interpolated pass drew the same world again a few milliseconds later and the tick's vertices were discarded wholesale — `planeD=8174` against `face=4087`. The tick draw was only there for two side effects: advancing per-tick visual state, and refreshing `ContO.dist`. Both now come from the single interpolated draw, which runs with `interpolating = !stepped` so a frame that ticked advances the effects exactly once and RECORDS the random sequence the following frames replay. **Measured, parked: stage 9 451 -> 706 frames in 25s (+57%, ~22 -> ~28fps mean), stage 1 677 -> 915 (+35%); frames over 100ms 9 -> 1 and 3 -> 0; frames under 20ms 64 -> 298 and 265 -> 607.** `?tickdraw=1` restores the second draw.
- **`restoreCurr` had to stop being total for that to work.** snapCurr is taken BEFORE the draw, because `applyBlend` needs the tick's positions — so restoring everything afterwards also rewinds what the draw legitimately produced. With the draw now authoritative, `dist` would freeze at whatever it held on the first frame and the draw PRNG bank would rewind every frame, so every effect would re-roll the same numbers forever. `recaptureDrawOutputs()` refreshes exactly `dist`, the draw bank and `MED_STATE` into snapCurr after an authoritative draw; everything else is still restored.
- **Caching polygon convexity at load is worth ~1%, not the batcher's 13%, and it is not sound anyway.** `isConvex` is inlined into `fillPolygon` and is ~29% of ITS ticks, and `fillPolygon` is 3.1% of a frame; the 13% is dominated by `_fillTrapezoid`, the CONCAVE path, which no convexity cache touches. And convexity here is a property of the PROJECTED polygon, not the model — a face folded around the camera arrives concave — so it cannot be hoisted to load time without drawing a fan over a self-intersecting outline. `isConvex` is now modulo-free instead (identical output, too small to measure on its own). The TASKS entry proposing the cache is struck.
- **The fill splits 1,895 fan polygons to 490 concave ones a frame (stage 9, parked), the concave ones carrying 3,699 vertices.** So a fifth of the polygons take a path costing roughly 4x per polygon. `rd.fanPolys`/`concavePolys`/`concaveVerts` are on the fps line. If the concave fill is ever attacked, that is the split to watch, and the backdrop's bowtie quads (known shape, always an hourglass) are the obvious special case.
