## 2026-08-01

- **Procyon mis-decompiles compound assignment.** `x += (int)(expr)` has TWO sources; disassemble each site. `i2f`/`i2d` on the LHS before the add = artifact, rewrite as `x = trunc(x + expr)`. Truncate-then-`iadd` = genuine, leave alone. ~45 sites in the keep set, 23 in `Mad.java`.
- **`*= (int)<float literal>` is ALWAYS an artifact.** `r3 *= (int)0.991` (black skybox) and `r6 *= (int)1.6` (checkpoint flash) are really `r3 = (int)(r3 * 0.991)`. Nobody writes a multiply-by-truncated-literal; don't "preserve" it as a game bug.
- **Every int op wraps at 32 bits, including the addition.** `Math.imul` on the terms is not enough — wrap the whole expression: `i32(Math.imul(a,a) + Math.imul(b,b))`. Reachable in practice: stage coords run to ±83000.
- **`Medium.sin`/`cos` return `float`.** Any expression touching them is float32 in Java; needs `fr()` at EACH binary op, not just at the end. Missing one drifts over frames instead of failing.
- **`Medium.random()` bottoms out in unseeded `Math.random()`.** `contO.zy`/`xy` are therefore NOT reproducible from a Java probe — three identical runs gave different values. Run any probe 3× before calling a mismatch a port bug.
- **In-race tick rate is 530ms per 10 frames (53ms, ~18.9Hz).** `GameSparker.java:1708`, `n5 = 530`. The 400ms figure is the MENU branch. Using 400 runs the game 1.325× too fast.
- **`java.awt.fillPolygon` is EVEN-ODD.** Checkpoint glyphs are keyhole polygons (bridge out to the counter and back). Ear clipping only works when the inner loop winds opposite the outer — true for "R", false for "O". Use a scanline even-odd fill.
- **No depth buffer anywhere.** Submission order IS depth. Never reorder, batch by material, or split primitive types into separate draw calls.
- **A default-constructed `CheckPoints` makes `Mad.drive()` hang forever.** `typ[]` all-zero spins `Mad.java:1600`; `nsp == 0` spins `Mad.java:1578`. Any probe must set `typ[]` positive and `nsp > 0`.
- **Don't `Unsafe.allocateInstance` a `ContO` for probes.** Constructor never runs, every reference field is null, and `drive()` NPEs on a different one each time you patch the last. Build it from a real `.rad` out of `models.zip`.
- **Verification pattern that works:** unpack `Game.jar`, drive the real class by reflection (`setAccessible(true)`), print state, diff against JS as exact integers. Probes live in `web/tools/`. `MadProbe` declares `package tools;` → run as `tools.MadProbe`.
- **`loadbase` self-checks:** summed uncompressed size of `models.zip` must equal 615671, else `mload = 2`.
- **Delegated transpilation jobs edited tests to make them pass — twice.** Never trust a green suite or a "gaps: none" report from a subagent; diff against an independent artifact and check the baseline file's checksum. `CarDefine.loadcar` was also silently stubbed to `return -1` (its own failure code) while the report claimed only networking was dropped.
- **`agy` quota is shared across `claude-*` and `gpt-oss`; gemini is a separate pool.** Run jobs ONE AT A TIME — five parallel opus jobs exhausted the quota and killed all five mid-flight.
- **Render resolution is free; tick rate is not.** The vertex shader divides by `u_size`, so raising the canvas backing store costs zero CPU. Raising the tick rate doubles game speed, because every constant in `Mad.drive()` is per-tick.
- **`GameSparker.draw()` is NOT pure.** It calls `Medium.d()`, which toggles `cpflik`, recomputes `elecr`, decrements `noelec` and advances `lilo`. Re-running draw at display rate for interpolation advances all of them 3× too fast — snapshot and restore them.
- ~~**Measured cost split (stage 1, 7 cars, ~8.9k tris):** `simulate()` 10.3ms, `draw()` 3.1ms.~~ WRONG — see the 2026-08-01 re-measurement below. Both the split and the triangle count were off.
- **"Render resolution is free" is WRONG** (entry above, superseded by measurement on the target machine). Vertex work is free; fragment bandwidth is not — no depth buffer means the painter's algorithm overdraws the whole scene, so 2x = 4x the overdraw. `antialias:true` multiplied it again, and the 2D overlay's per-frame full-size `clearRect` was a CPU cost that also scaled with `?res=`. Overlay is now sized by `?textres=` (default 1) and MSAA is off above 1x.
- **The static host sends no `Cache-Control`.** An ES module graph then goes stale one file at a time: you get the new `main.html` and last deploy's `graphics.js`, and the change looks like it didn't ship. `deploy.sh` stamps every relative import and `<script src>` with `?v=<md5 of sources>`.
- **Real cost split, measured in-browser (stage 1, res=2):** 1 car — sim **0.61ms**, draw **14.60ms**, 47k verts. 8 cars — sim **1.72ms**, draw **24.38ms**, 100k verts. Physics is 2-7% of the tick; DRAW IS EVERYTHING. Cost tracks vertex count at ~0.25µs/vert. Static stage geometry is ~40k verts, re-projected on the CPU every frame though it never moves.
- **Draw layers, measured properly (8 cars, res=2, ns/vert normalised):** overlay **1.8%**, geometry batching **19%**, projection/traversal **81%**. This SUPERSEDES the ~50/50 figure below, which credited a lighter scene as a saving because `raster=0` reported zero verts and could not be normalised.
- **Cost model from two browser runs:** `draw = ~9.8ms fixed + ~1.01us per PROJECTED vertex`. Projected != submitted: `Plane.d` transforms 12-20 vertices per face (the `master===1` LOD switch) before culling decides whether to submit any, so 14,799 vertices are projected to submit 10,263 (1.44x). Node agrees on the slope (0.65us) but shows only 1.4ms fixed; the browser's 9.8ms fixed term is NOT accounted for -- `medium.d()`, the backdrop, is only 1.8ms/16%.
- **Nothing counts the even-odd scanline fill's cost, which is proportional to polygon AREA, not vertices.** Checkpoint glyphs on screen in one run and not another moves the fixed term with no counter changing. Suspect this before trusting a fixed-cost figure.
- **Array pooling is a 30% PESSIMISATION** (10.96ms -> 14.27ms, node, same scene). The "1.13x, bit-identical" entry above was wrong, and the in-game A/B that appeared to show no difference compared fps -- which is pinned at 18.9 with `interp=0` and could not have shown anything. Leave `?pool=` off.
- **Scene shape is reproducible in node to within 0.1%** (faces 1956/3261 for 1/8 cars, matching the browser exactly). Use `web/` under node to get counts and ratios without a browser round trip; only absolute timings need the real thing.
- **Draw splits ~50/50 between projection and the batcher** (8 cars, res=2, `?raster=0` isolates it): 24.09ms normal vs 12.53ms with the emit calls no-op'd. So per-vertex projection in `Plane.d` is 12.5ms and triangulation + vertex-buffer writes in `graphics.js` are 11.6ms. Moving projection alone to a vertex shader is worth ~2x, not 4x.
- **Timing `GameSparker.tick()` as a unit reports `draw 0.00ms`.** `tick()` is `draw()` then `simulate()`, so with interpolation off the entire draw cost lands in the "sim" number. Time the two halves separately — this is what produced the bogus 10.3/3.1 split above.
- **With `interp=0` the game draws only on a tick, so fps is pinned at 18.9 by construction.** Comparing render settings by fps in that mode always reads flat; use the ms figures. Interpolation is now the DEFAULT (~58fps measured); each interpolated frame still costs a full CPU redraw, so draw cost is what caps the frame rate.
- **`Medium.follow()` is a stateful ease, not a function of time.** Re-running it per interpolated frame gives one ease step from the restored tick state every frame, so the camera lurches once per tick no matter how smooth the objects are. Interpolate the camera's own two tick states instead. The `cam=derive` mode built on this was removed.
- **`Math.imul` on a float operand silently zeroes it.** `Mad.colide`'s narrow-phase threshold is `(n3 + n4) * (comprad[a] + comprad[b])`; `comprad` is a `float[]` (formula7 = 0.4), so the port's `Math.imul` truncated the sum to 0 and the threshold became 0 — **no car in the default field ever collided**. Use `Math.imul` ONLY when both operands are `int` in the Java; check the field's declared type, don't infer it from the values. Audited: `CarDefine.powerloss` was the only other candidate and is genuinely `int[]`.
- **Two identical cars never collide, and that's authentic.** `colide()` picks a dominant car by `|power * speed * moment|`, then by `moment`; on an exact tie neither dominates and no contact is evaluated. Any collision test must make the two cars asymmetric or it silently tests nothing.
- **The concave fill was emitting one quad per pixel ROW.** Replaced with a trapezoid decomposition (cut at every vertex y AND every edge-edge intersection y, one trapezoid per span per band): 40,041 -> 25,455 verts/frame, 8.4% CPU. Both are exact even-odd; verified against a point-in-polygon truth, not against each other.
- **Backdrop quads arrive ordered TL, TR, BL, BR — bowties.** `java.awt` fills those as an hourglass, so even-odd is REQUIRED and a triangle fan would fill the bounding quad. Any fill rewrite must keep intersection ys as band boundaries or the left-to-right span pairing is wrong inside the band containing the crossing.
- **`medium.d()` (the backdrop) was 6.38ms/frame, 34% of draw** — and it was mostly the scanline fill, not the band geometry: the trapezoid fill took it to 3.83ms (-37%) with no other change. Confirmed in-browser at matched scene weight (9,519 vs 9,476 submitted verts): emitted 57,069 -> 37,269, 2146 -> 1888 ns/vert. The "fixed cost that scales with nothing" was largely an O(polygon height) term.
- **A within-run regression of draw-ms against scene weight is ill-conditioned.** It returned a NEGATIVE fixed cost (-3.44ms) and a higher slope for a run doing strictly less work. Slope and intercept trade off when the x-range is narrow. Report R^2 and the x-range, and prefer a direct stopwatch (`?prof=1`) over a fitted intercept.
- **`loadbase` puts track pieces at slot `j + 56`, not `j + 16`.** Cars are 0-15 but there is a gap before the track models. Assuming they were contiguous mislabelled every placed object and silently defeated a filter that keyed on the name. Import `CAR_NAMES`/`TRACK_NAMES` from `GameSparker.js` rather than copying them.
- **`Medium.trk !== 0` is what makes an overhead view possible.** `ContO.d`'s distance-fade and minimum-projected-size culls are both written `... || this.m.trk !== 0`, so at map zoom only 7 of 190 objects survive with `trk = 0`. `trk = 2` is the StageMaker's overhead editing mode (`StageMaker.java:886`) and keeps decor; `trk = 1` hides it.
- **The stage knows its own extent; don't infer it from object positions.** `maxl`/`maxr`/`maxt`/`maxb` in the stage file are the four boundary walls, and `loadstage` passes exactly those to `trackers.devidetrackers()`. So after a load, `trackers.sx / sz / ncx*3000 / ncz*3000` IS the game's own bounding box. Deriving one from object positions is both wrong (outliers skew the centre) and unnecessary.
- **The renderer cannot do a whole-stage overhead view of a large stage.** The StageMaker's own overhead mode stops at `m.y = -15000` and SCROLLS. Stages 1/3/9 render at ~67-81k depth; stage 8 at ~91k emits 24 verts for 172 objects that pass every gate checkable by hand. Cause is inside `Plane.d` and is NOT understood. The launcher falls back to a flat map past 85k.
- **`ContO.d`'s `crs` shadow assumes the object sits on a track.** A car floating at `y = 0` gets the silhouette drawn across its middle; seating it at `y = ground - grat` (what loadstage does) makes the shadow the entire frame. Previews should just turn `shadow` off.
- **`Medium.sin`/`cos` are 360-entry tables indexed by WHOLE degrees**, so an interpolated frame could not express a heading between two degrees and had to round. At ~800px across a ~60-degree view that is ~13px of yaw per step: interpolation translated smoothly but rotated in 13px jumps, which is why `?interp=1` was jittery ON TURNS AND ONLY ON TURNS. Both now lerp between neighbouring entries for a fractional argument; an integer argument takes the identical branch, so the simulation is untouched and stays bit-identical.
- **The HUD is drawn from `simulate()`, not `draw()`, and it is BOTH kinds of drawing.** Labels and images go to the 2D overlay; the damage/power bars and the checkpoint arrow are GEOMETRY in the same batch as the scene. Both are emitted once per TICK, so an interpolated frame drops both unless handled: keep the overlay (`begin(true)`) AND replay the geometry `simulate()` produced (`snapshotFrom`/`replay`). Fixing only the overlay left the meters reading zero and the arrow missing — the failure looked like a game bug rather than a frame-composition one.
- **A canvas keeps one context type for life,** so a 2D fallback cannot share the WebGL canvas -- `getContext('2d')` returns null. And an author `canvas { display: block }` beats the UA stylesheet's `[hidden]`, so a hidden canvas still takes up space.
- **Headless Chromium won't run rAF without `--screenshot`.** `--headless=new --virtual-time-budget=N --dump-dom` boots the page, runs GL, and never fires a single animation frame, so the game appears hung. Adding `--screenshot=x.png --window-size=800,450` drives the compositor and it runs. This is the cheapest way to verify a browser change end-to-end (`--enable-logging=stderr --vmodule=console=1` to read `console.log`).
