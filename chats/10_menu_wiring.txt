❯ why cant we hardcode a peerjs room as the lobby, then create separate codes   
  for the rooms?  one sen                                                       

● That works, and it's the best idea on the table — with one catch: a PeerJS id
  is exclusive, so nfm-lobby is held by exactly one browser tab, and that tab is
  the directory server.

  Which gives:

  - Claim-or-connect election. On opening Multiplayer, try new 
  Peer('nfm-lobby'). Success → you're the directory: hold connections from hosts
  announcing {code, name, stage, players} and serve the list to browsers. Error
  unavailable-id → connect to it as a client instead. No backend, no
  provisioning, and it's ~60 lines.
  - The directory dies with its tab. Everyone sees the connection close and
  re-runs the election; the winner takes the id and every host re-announces.
  Recoverable, but there's a gap of a second or two, and this is exactly the
  host-migration complexity you dropped for the race — worth accepting here only
  because losing the directory costs a stale list, not a race.
  - Empty when nobody is in the menu. If all players are mid-race with no one
  sitting on the Multiplayer screen, there's no directory and the list is empty
  even though games exist. Mitigable by having hosts claim it preferentially (a
  host is a long-lived tab), so the directory lives as long as any game does.
  - Anyone can squat or forge it. The id is public and unauthenticated — a bad
  actor can hold nfm-lobby and serve a fake list. Same trust model as the rest
  of the netcode, so not a new concession, but it means the list is a
  convenience and the room code is still the real join path.
  - Announce over the reliable channel, and the directory can ping each host for
  a live player count instead of trusting the announcement's.

  Practical version: build room-code Host/Join as the load-bearing path, and put
  the directory behind it as the list that populates the mockup's browser when
  someone's holding it. If the election turns out flaky in practice, the screen
  still works.

❯ so p2pt is more featureful in that it allows one↔many, and this cant be       
  constructed with peerjs?                                                      

● Right — p2pt's extra feature is discovery, not the connections: it announces
  to public WebTorrent trackers under a swarm identifier and the tracker hands
  back everyone else on that identifier, which is the rendezvous PeerJS's broker
  deliberately doesn't offer.

  With PeerJS you can build the many↔many part fine (once you know N ids, you
  open N connections), but there's no way to learn the ids — so it can only be
  constructed by fixing an id in advance, i.e. the squatter directory. p2pt
  replaces our broker entirely (its own trackers, its own DataChannels), so
  adopting it for the game list would mean either running both transports side
  by side or moving the whole netcode onto it.

❯ downside of reliable is latency?  one sen.  if yes, can we profile simply?    
  (you can use other device `cop` over ssh for test)                            

● Yes — reliable+ordered means one lost state packet head-of-line blocks every
  later one until it's retransmitted, so a drop costs ~1 RTT of frozen cars
  while the retransmitted position is already worthless (absolute state
  supersedes itself).

  Profiling it is cheap and needs no browser: netloop.mjs already runs N clients
  through a lossy relay with configurable loss/latency, so adding a
  head-of-line-blocking mode to the relay (hold subsequent packets for one RTT
  on a drop, deliver in order) gives you a direct A/B of steady-state residual
  and worst correction, unreliable vs reliable, at 0/10/30% loss. That's the
  number that decides the swap.

  For a real-network figure, cop over ssh can run one client while this machine
  runs the other, but netloop's clients talk over stdio to a parent relay — so a
  real-network run needs a socket transport added to the harness first, which
  is a bigger job than the emulated A/B and I'd only do it if the emulated
  numbers land close.

  Want the emulated A/B run?

● Ran it. netloop.mjs gained a reliable mode: a lost packet is retransmitted a
  round trip later instead of dropped, and every packet behind it on that link
  waits for it. Same worlds, same noise seed, same everything else.

  ┌──────┬─────────┬───────────────────────────────┬───────────────────┐
  │ loss │ latency │ steady residual (unrel → rel) │ worst stall (rel) │
  ├──────┼─────────┼───────────────────────────────┼───────────────────┤
  │ 0%   │ 2 t/hop │ 22 → 3                        │ none              │
  ├──────┼─────────┼───────────────────────────────┼───────────────────┤
  │ 2%   │ 2 t/hop │ 46 → 9                        │ 3 ticks (~160ms)  │
  ├──────┼─────────┼───────────────────────────────┼───────────────────┤
  │ 10%  │ 1 t/hop │ 10 → 28                       │ 5 ticks           │
  ├──────┼─────────┼───────────────────────────────┼───────────────────┤
  │ 10%  │ 2 t/hop │ 24 → 101                      │ 11 ticks (~580ms) │
  ├──────┼─────────┼───────────────────────────────┼───────────────────┤
  │ 30%  │ 2 t/hop │ 40 → 354                      │ 19 ticks (~1.0s)  │
  └──────┴─────────┴───────────────────────────────┴───────────────────┘

  At realistic loss, reliable is not worse — it's better. At 0–2% it beats the
  unreliable arm outright (22→3, 46→9 units), because the unordered channel's
  15% reordering costs more than the occasional retransmit does. A car is ~200
  units across, so single-digit units is invisible.

  It falls apart above ~10% loss: residual 101 units at 10% and 354 at 30% (the
  limit is 400), the trail offset doubles from 2 ticks to 4, and the stalls
  reach 11–19 ticks — that's a car frozen for half a second to a full second,
  which is not what render-side smoothing fixes. Smoothing hides a transient
  snap; a persistent 100–350 unit offset plus a visible freeze is a different
  failure.

  Caveat on the model: retransmit is a plain RTT-timer geometric retry, no
  fast-retransmit or SACK, so real SCTP will do somewhat better than this at low
  loss and about the same at high. And these are single runs on one fixed noise
  seed.

  So p2pt is on the table — reliable-only costs nothing on a healthy connection,
  and the loss regime where it hurts is one where the game is already
  unpleasant. The thing it would still cost you is the second channel split:
  today the join handshake and chat ride a separate reliable channel precisely
  so they don't compete with state, and on one channel a chat message queues
  behind state packets (and vice versa).

  The harness change is uncommitted and nothing else was touched. Want me to
  commit it and log the finding in WORK.md, and should I plan the launcher
  against p2pt or stay on PeerJS?

● Because in p2pt the connection is the only channel for app data — the tracker
  relays SDP offers and nothing else, so "I am hosting, stage 3, 2/8 players"
  has to travel over a DataChannel that by then already exists. There's no
  payload field in the announce for it.

  Three ways out, in increasing order of how much they cost you:

  1. Encode the advert in the peer id. BitTorrent peer ids are 20 bytes chosen
  by the client, and every peer on the identifier sees them in the tracker's
  response before any connection. A host can pack NFM + a 6-char room code + a
  stage byte + a player count into that, and browsers read the list straight
  from the announce with zero WebRTC. Costs: ~16 usable bytes, so no game name
  unless you shorten everything else; no ping; and the count only refreshes when
  the host re-announces under a new id, which p2pt would need patching to do.
  2. Patch p2pt to not auto-answer. The tracker hands you an offer and p2pt
  immediately answers it; hold the offers instead and answer only for the room
  you're joining. You then get presence-only discovery — "six people are on the
  nfm identifier" — with no metadata at all unless combined with (1).
  3. Keep one connection per host, not per peer. Guests connect to hosts only,
  never to each other, on the directory identifier. That's the cheap 80%: with
  five hosts and thirty browsers it's thirty connections rather than a 35-way
  mesh. Still needs p2pt patched to be selective about who it answers.

  All three need p2pt patched, because auto-connecting to everyone on the
  identifier is the library's whole model. The honest comparison is that the
  current design costs one wasted connection per idle client and zero patching,
  and (1) is the only one that removes the connection entirely.

  My read: the second rendezvous is the thing actually hurting (a minute to
  join), and making rooms virtual fixes that without touching p2pt — the
  connection you'd be "wasting" is the one you were about to need anyway. I'd do
  that first and only reach for peer-id adverts if the global mesh becomes a
  real problem.
