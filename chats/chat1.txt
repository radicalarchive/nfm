● I dug through the jar before answering. Short version: this is a 
  better-than-average CheerpJ candidate, and the cheapest way to find out is to 
  just try the existing jar unmodified — probably 30 minutes of work.

  Why it's a good fit

  - Pure AWT, no native anything. 52 classes, all major version 50 (Java 6).
  Rendering is java.awt.Graphics2D primitives — drawString, drawLine, fillRect,
  fillPolygon, drawImage. No LWJGL, no Java3D, no JNI. CheerpJ 4.3 runs
  unmodified jars and implements AWT/Swing onto a canvas, so there's nothing
  structurally in the way.
  - It's already a static-asset app. One jar plus data/, stages/, music/ —
  that's a static web host, no server.
  - Madness.fpath is a gift. It's a single static String, built from argv in
  main(), prefixed onto all 117 file accesses in the codebase. That means you
  control read/write root from JS (cheerpjRunMain args) without a new bytecode
  patch — which matters, because /app/ is read-only HTTP and saves have to land
  in /files/ (IndexedDB).
  - Your existing patches carry over cleanly. The runFinalizersOnExit NOP and
  the keyDown/keyUp null guard are still wanted; the bitDepth fix becomes moot
  but harmless.

  Real risks, roughly in order

  1. Performance — the actual unknown. This is a software 3D renderer pushing
  per-frame Java2D calls with antialiasing on. CheerpJ is fast but not free.
  Note your 2× buffer patch (1600×900) quadruples per-frame fill cost — in the
  browser I'd make that a toggle and start at 800×450.
  2. Fullscreen is dead as written. gofullscreen() uses
  GraphicsDevice.setDisplayMode / setFullScreenWindow. Needs neutering and
  replacement with a JS canvas-fullscreen + cheerpjCreateDisplay sizing. Your
  patches #6/#7 (auto-fill, slider default) are the right hooks to build on.
  3. Runtime.exec (5 sites) and Desktop.browse (4 sites). From
  advopen/openurl/checknupdate — plus string constants for data/adv.bat and
  data/madapp.jar. These don't exist in a browser. The danger isn't that they
  fail, it's that one fires during startup and hangs or throws before the menu
  draws.
  4. Networking is gone. Socket, DatagramSocket, InetAddress across
  Lobby/Login/UDPMistro/udpServe/update. Browsers give no raw TCP/UDP (CheerpJ's
  only escape hatch is a Tailscale WebSocket proxy). Since radicalplay.com has
  been dead for a decade, the goal is just making sure nothing blocks on a
  socket at load.
  5. Audio. javax.sound.sampled Clip/SourceDataLine plus the ibxm/ds.nfm.mod MOD
  player — mixing happens in Java. CheerpJ supports audio, but browser autoplay
  policy needs a user gesture first, and Java-side mixing is a stutter risk.
  6. CarMaker/StageMaker are the shakiest. They lean on FileDialog, PopupMenu,
  TextField/TextArea, JOptionPane. I'd treat the racing game as the deliverable
  and the editors as stretch.

  What I'd do next

  Skip the planning and get a signal: serve the directory statically, point
  cheerpjRunMain("Madness", "/app/Game.jar", ...) at the current jar, and watch
  where it stops. That one experiment answers perf, audio, and startup-hang
  questions better than any amount of further static analysis — and every
  failure it surfaces is a concrete patch in the same ASM workflow you already
  have.

  Want me to set that up? I'd add a web/ dir with the loader page and a small
  static-server script, leaving Game.jar and the desktop path untouched.

  I tested it rather than guessing, and the answer is stronger than I expected:

  So: your current approach was correct, and is now the wrong one going forward.

  It was correct because ASM-on-pristine-bytecode is deterministic and sidesteps
  decompiler-fidelity risk — a reasonable default when you have no source and
  are making three surgical edits. But the browser port changes the arithmetic.
  The edits ahead of you are no longer surgical: neuter gofullscreen(), delete
  the checknupdate() call, stub Runtime.exec/Desktop.browse, rework sizing to
  come from cheerpjCreateDisplay instead of DisplayMode. Expressing those as
  byte-offset pokes and ASM InsnList splices is a lot of pain for edits that are
  five lines of Java each — and offset-based patches like Madness.class offset
  6461 silently rot the moment anything above them shifts.

  What I'd do:

  1. Move the build inputs into the repo now.
  /tmp/opencode/{orig,build,Patcher.java} still exists, but it's in /tmp —
  Debian clears that on boot. The build documented in AGENTS.md is currently one
  reboot away from unreproducible. That's the actual bug here, independent of
  the source question.
  2. Promote Madness.java and GameSparker.java to real source, decompiled from
  the patched classes so your seven existing patches carry over as readable
  code, then compiled by javac as a normal build step. Retire Patcher.java and
  the byte-offset patches with it.
  3. Leave the other 50 classes as opaque binaries. Don't decompile what you
  don't edit — no round-trip risk you don't need, and xtGraphics at 151KB is
  exactly where a decompiler is most likely to produce something subtly wrong.
  4. Keep a full decompile as read-only reference, regenerated on demand and
  marked non-authoritative. It's greppable and it earns its keep — reading
  checknupdate() and main() above took seconds and turned up both the fpath
  lever the web page now uses and the fact that a successful update check
  overwrites Game.jar.

  The one rule that matters: one authority per class. Never let an ASM patch and
  a source edit touch the same file, or you'll have two sources of truth that
  drift.

  repack, and confirm the game still runs identically on the desktop. Want me to
  do that switch, or run the browser smoke test first and let the results shape

  Is a JS/wasm port feasible?

  I measured the surface rather than eyeballing it. 314 distinct JDK methods
  across the whole game. The split is what matters:

  - Rendering: 42 methods, and they're nearly all one-liners in Canvas2D.
  fillPolygon → path + fill, drawString → fillText, setComposite(AlphaComposite)
  → globalAlpha, drawImage → drawImage. This is the encouraging number, and
  it's unusually small because the game was written for Java 6 AWT and never
  grew past it.
  - ~400KB of core bytecode — xtGraphics (151KB), GameSparker (61KB), ContO
  (40KB), Mad (34KB), Medium (32KB), Control (24KB), Plane (18KB). Dense 3D math
  and game logic. This is the discouraging number.

  that 400KB — a sign flip in a rotation, an off-by-one in a polygon index —
  doesn't crash. It makes the handling subtly wrong, and no test suite you can
  write will catch it. Which is why your offer to do sequential human testing
  genuinely changes my answer: that failure mode is only catchable by a person
  driving the car and saying "this feels wrong." With you in the loop, a staged
  port is tractable in a way it otherwise isn't.

  Three routes, ranked:

  1. CheerpJ + targeted Java patches (current). Cheapest by far — we're one bug
  in. Costs: ~20MB runtime download, weak control over fullscreen and input,
  debugging through two layers.
  2. TeaVM + a Graphics2D→Canvas shim. The one I'd reach for if CheerpJ
  disappoints. TeaVM AOT-compiles bytecode to JS/wasm but ships no AWT —
  normally fatal, but here you'd shim

  3. Full hand/LLM port to JS. Most control, most risk. Justified only if you

● Bad performance, not a mistuned constant — and the loop tells us how much of
  each.

  GameSparker.run() ends with an adaptive pacer:

  long millis = Math.round(a) - (time3 - time2);   // budget minus actual frame 
  time
  if (millis < n4) millis = n4;                    // n4 = 15 in-race, 30 in 
  menus
  Thread.sleep(millis);

  a is a feedback-controlled budget: every 10 frames it nudges ±3.5ms to hold 10
  frames ≈ 400ms, and floors at 5.0. So on a machine too slow to keep up, a
  bottoms out and the sleep clamps to the floor — meaning the pacing logic can 
  only ever add 30ms per menu frame. A 33fps ceiling, not a 4fps one. Your 250ms
  frames are ~220ms of real work plus that floor. The constants aren't the
  problem; something genuinely costs 220ms.

  The prime suspect is our own patch #4. The offscreen buffer is
  createImage(1600, 900) with rd.scale(2,2) and antialiasing on, and paint()
  then does a scaled 10-arg drawImage of that full 1600×900 buffer every frame.
  That's 4× the fill area plus a per-frame scaled blit — cheap on a desktop JVM
  with a hardware-backed VolatileImage, potentially brutal in CheerpJ where it's
  canvas operations.

  The one-minute A/B that settles it: run the pristine jar, which is still
  sitting there untouched.

  http://localhost:8000/web/?jar=/app/Game.jar.bak

  Game.jar.bak is the original 800×450 build. It won't run on your desktop Java
  19 — but it will run here, because CheerpJ is a Java 8 runtime and
  System.runFinalizersOnExit still exists there. So it's a clean baseline: same
  CheerpJ, same everything, minus the 2× buffer. If the menus jump to ~30fps,
  the patch is the cost and the fix is a browser build at 1×. If it's still
  ~4fps, CheerpJ's Java2D is simply too slow for this renderer and route 2
