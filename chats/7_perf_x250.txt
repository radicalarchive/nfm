● The bug

  browser2p.mjs:36:

  if (page) return new WebSocket(page.webSocketDebuggerUrl);

  WebSocket became a global in Node 22. This machine runs Node 18.19, where
  typeof WebSocket === 'undefined' — I just confirmed it. So that line throws
  ReferenceError: WebSocket is not defined.

  Why it's nasty rather than merely broken

  The line sits inside this loop:

  try {
    const list = await (await fetch(...)).json();
    const page = list.find((t) => t.type === 'page');
    if (page) return new WebSocket(page.webSocketDebuggerUrl);
  } catch { /* not up yet */ }     // <- swallows the ReferenceError too

  The catch is bare. It was written to absorb one specific expected failure —
  the browser hasn't opened its debugging port yet — but it catches everything,
  including a programming error that will never resolve no matter how long you
  wait. So:

  1. fetch succeeds. The browser is up and healthy.
  2. A page target is found.
  3. new WebSocket throws.
  4. The catch discards it as "not up yet".
  5. 60 retries × 250 ms later: throw new Error('no devtools on 9333').

  The error you get names the browser and the port — the two things that are
  actually fine. Nothing anywhere mentions WebSocket.

  That's the trap I walked into. spike.mjs started as a copy of this connect
  loop, and I spent several rounds on chromium flags, a stale profile lock,
  detached spawning, and a genuinely misleading bind() failed: Address already 
  in use in the stderr log, all chasing a message that pointed away from the
  cause. It only surfaced once I made the loop record why each attempt failed
  rather than discarding it — which is the general lesson: a retry loop that
  swallows the reason is a retry loop that will eventually lie to you about what
  went wrong.

  Scope

  shot.mjs:38 has the identical line and the identical bare catch. netloop.mjs
  and netclient.mjs are clean — they don't use CDP.

  Worth being precise about one thing: this is almost certainly an environment
  regression, not a code one. WORK.md records browser2p.mjs successfully driving
  two browsers through a netplay race on 2026-08-02, so it worked against some
  newer Node. The file hasn't changed; the interpreter available to it has. I
  can't tell from here whether Node was downgraded or those runs happened
  elsewhere.
