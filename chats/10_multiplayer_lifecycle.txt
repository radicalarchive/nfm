● A room is just a name, and a tracker is a public bulletin board that tells you
  who else is standing under that name. Steps:

  - Name the room — the room code (e.g. PQ7K2M) is prefixed to nfm- and hashed
  into a WebTorrent "info-hash", a 20-byte id. Host and guest doing this
  independently get the same id, so nothing needs to be exchanged but the code
  itself.
  - Open a websocket to the trackers — the browser connects to 3 public
  WebTorrent tracker servers (netpeer.js:48). They are strangers' servers, run
  for file sharing; we borrow them purely as a meeting point.
  - Announce — "I am peer <random id>, I'm interested in <hash>". Hosting a room
  is nothing more than this (openRoom → #enter → wait for trackerconnect,
  netpeer.js:263); there is no server-side room object anywhere. This is also
  the first slow bit — you wait on a tracker's schedule and its round trip.
  - Get handed the peer list — the tracker replies with other peers announcing
  the same hash. Joining a room is the same announce; the difference is only
  that the guest then waits for someone to appear (join, 45s timeout).
  - Swap WebRTC offers through the tracker — each side generates a connection
  offer/answer (its IP candidates, crypto keys) and passes it through the
  tracker as an announce payload. The tracker is a message relay for these blobs
  and nothing more.
  - Punch through the NATs (ICE) — the two browsers try every candidate address
  pair until one works directly, home router to home router. Second slow bit,
  and the flakiest one.
  - DataChannel opens — peerconnect fires, we hand the peer an index, and the
  tracker's job is over; it could go offline mid-race unnoticed.
  - Everything after is direct — one reliable/ordered channel per peer, first
  byte tagging chat/lobby vs. car state. This is why a track change lands
  instantly: no tracker, no host relay, just the wire.
  - Full mesh, done N times — every peer meets every other peer via the same
  list, so guest-to-guest traffic is direct. The host is special only in that it
  assigns slots and owns the bots, not in routing.
  - The game browser is the same trick — every idle client on the Multiplayer
  screen announces on one well-known name, nfm-directory-v1, and hosts reply
  with their room details.

● Not quite — seeing the announcement is only the introduction; A must then send

  What I found

  The root cause is a race in p2pt, and we trip it every single time.

  new P2PT(urls, id) calls an async setIdentifier() and never awaits it. start()
  awaits the hash promise, not that method — so _infoHashBinary, which the
  announce actually reads, is still undefined when the first announce is
  assembled. It gets away with this when the websocket has to be dialled first
  (the announce defers to the socket's connect event, by which time the hash has
  landed). It does not get away with it when the socket is already open — and
  bittorrent-tracker pools websockets per tracker URL across every p2pt in the 
  page. Hosting or joining opens a room swarm while the directory swarm already
  holds those sockets. So the room's first announce always goes out malformed.

  The blast radius is much worse than a dropped announce. Captured live:

  WS -> tracker.webtorrent.dev announce 5 offers
  keys=numwant,uploaded,downloaded,action,peer_id,offers   ← no info_hash
  WS NO-ACTION tracker.webtorrent.dev {"failure reason":"Invalid request"}
  [host] DIR  trackerwarning: invalid action in WS response: undefined
  [host] ROOM trackerwarning: invalid action in WS response: undefined

  The tracker rejects it with a failure reason and no action field;
  bittorrent-tracker treats an unrecognised action as a socket error, so it
  calls destroy() and reconnects on a backoff of 10s plus up to 300s of jitter.
  Because the socket is shared, that takes the directory down along with the
  room — both instances fire, as the two warning lines show.

  That "invalid action in WS response: undefined" is the same warning we 
  diagnosed as harmless tracker noise and routed to console.warn. It was the
  symptom of this, not chatter from a flaky tracker.

  Measurements

  - The trackers are fast. Raw websocket test, two fake peers: a newcomer's
  offer reaches the sitting peer in ~120ms. Announce interval is 120s, but it's
  irrelevant — the newcomer's own announce is what does the work.
  - Bare p2pt is fast. Two real browsers, one swarm each: datachannel open
  ~900ms after the guest starts.
  - Our shape is not. Same two browsers with a directory swarm running first:
  room trackerconnect at +9.7s / +42s / +55s across runs, and in one run the two
  never connected inside 60s.
  - browserlobby.mjs end to end: host opens a room in 1.6s, guest sees it listed
  in 2.4s — then the join takes 31.5s.
  - With the hash awaited: room trackerconnect +306ms, peer connected ~400ms
  after the guest announced, zero rejected announces, no tracker destroyed.

  That maps onto all three of your symptoms: hosting is fine-ish because the
  first swarm is the directory; joining is the slow one because it's always the
  second swarm; and "sometimes it never shows up" is a tracker sitting out a
  10–300s backoff. tracker.btorrent.xyz is also simply unreachable from here, so
  we're often down to one working tracker when this fires.

  Two other things worth knowing (not fixed, not urgent)

  - requestMorePeers() every 5s is heavier than it looks. Each call announces to
  all 3 trackers, each announce generates 5 fresh RTCPeerConnections (trickle: 
  false, so each waits for ICE gathering), and each is held 50s before timeout —
  up to ~150 live peer connections per client. Given the measurement above (a
  newcomer's own announce is what makes discovery work), this polling is mostly
  redundant; it was added to fix the game-list unreliability that this bug was
  actually causing.
  - p2pt sets iceServers: [] — no STUN at all. Fine on a LAN or localhost; two
  players behind different NATs have only host candidates to work with and may
  never connect. Untested here, and it would look exactly like "sometimes it
  doesn't work".

● No, one swarm is enough — and it's the fix for the slow join, not a workaround
  for it.

  The two swarms exist because the room code was made an identifier (a
  rendezvous point). But by the time you click a game in the list you are
  already connected to that host over the directory mesh — the join then throws
  that connection away and pays a second full tracker+ICE rendezvous to rebuild
  the same link under a different name. That second rendezvous is both the 30s
  wait and the thing that trips the p2pt hash race.

  The simpler architecture: one well-known identifier (nfm-v1), and a room
  becomes a label carried in frames rather than a swarm. The frame tag byte
  already in netpeer.js grows a room field; presence, the game list, lobby
  roster, chat and race state all ride the connections you already have. Joining
  a listed game becomes a message, not a network operation — instant, and it
  cannot fail on tracker backoff. Join-by-code works identically: you enter the
  shared swarm, then address the host by code.

  What it costs, honestly:
  - Everyone idle in the menu meshes with everyone else idle in the menu, not
  just their own game — fine at this game's scale, quadratic if it ever isn't.
  The bound is to leave the shared swarm when the race starts, keeping only your
  game's peers; a racing client has no use for the list anyway.
  - The room code stops being cryptographic separation and becomes an in-band
  credential the host checks. That is a real reduction, but a small one: the
  design is already unauthenticated, and the code was never secret from the
  trackers.
  - netcodec/netsession are untouched — they're slot-general and never knew
  about swarms.

  What it deletes: the second p2pt instance, the socket-pool collision,
  requestMorePeers polling, JOIN_TIMEOUT_MS, and the "guest never saw the game
  listed → fall back to join-by-code" branch in browserlobby.mjs.

  One caveat before committing to it: I've measured the directory swarm with 2–3
  peers, not 20. The mesh cost and the tracker's willingness to relay offers to
  a large swarm should be measured before this becomes the shipped design.

❯ explain in a numbered list what happens under the hood when a player logs on,

● Proposed one-swarm design (current design noted where it differs):

  1. P1 opens the Multiplayer screen. Browser hashes nfm-v1 into an info-hash,
  opens websockets to the 3 trackers, and announces on it carrying 5 WebRTC
  offers. Nobody else there — announce reply says so, nothing more happens.
  2. P1 clicks Host. Purely local: mint a room code, build the Lobby, set
  listing = {code, name, stage, players, max}. No network operation at all —
  this is the step that currently opens a second swarm and takes seconds.
  3. P2 opens the Multiplayer screen. Same hash, same trackers, announces with 5
  offers.
  4. The tracker pushes P2's offer to P1 unsolicited on P1's existing socket
  (~120ms measured). P1's RTCPeerConnection answers, the answer goes back
  through the tracker, ICE picks a candidate pair, and the DataChannel opens —
  ~1s end to end.
  5. They exchange presence over that channel. P2 sends who, P1 replies game
  with its listing; P1's row appears in P2's list. Ping is a round trip on the
  same channel. (This much already works, and is the fast part today.)
  6. P2 clicks the row. Sends join with the room code down the already-open
  channel. No tracker, no ICE, no new swarm — this replaces today's second full
  rendezvous and its 30s.
  7. P1 seats P2: checks the code, assigns the slot (host's alone — two guests
  choosing for themselves collide), and replies with the roster; both render the
  lobby. P2's roster arrives on the same channel that delivered the listing, so
  the hello-dropped-before-a-handler-exists class of bug can't recur.
  8. P1 re-announces its listing to every peer, so anyone else browsing sees the
  player count tick to 2.
  9. A third player repeats 3–4 and meets both directly — the mesh is already
  full, so guest-to-guest state needs no relay.
  10. Host presses Start. Seed, stage, grid and slot assignment ship verbatim
  from the host; every client boots the world from them, then leaves the shared
  swarm and keeps only its game's peers — which is what stops the mesh growing
  with the number of idle browsers.

  Both bugs you hit are one root cause

  A networked race never tells the game it is networked. main.js sets xt.fase =

  - XtGraphics.js:1106 — when you're wasted with ≥2 players still alive, the

  the host spectates indefinitely. Worth deciding deliberately rather than
  inheriting.

  What else the lifecycle walk turned up

  1. Nothing anywhere handles a disconnect. NetPeer.onClose is assigned by no
  one — not Lobby, not launcher.js, not main.js. Consequences at three points:
  - In the lobby: a guest that closes its tab stays on the roster forever, keeps
  inflating the advertised player count, and gets seated into the race with a
  car nobody drives.
  - If the host leaves the lobby: guests are never told and sit on a dead lobby
  screen indefinitely. leaveLobby() sends no message either — it just drops the
  connection.
  - In a race: the departed car dead-reckons forever on the last control flags.
  It never becomes dested, so "all cars wasted" can never be satisfied and that 
  race cannot end. The original's answer is dested[i] = 3 and discon, both of
  which are also behind fase === 7001.

  2. The race start is not gated on both worlds existing. Lobby.start() sends
  start and resolves immediately; each client then does its own
  loadbase/loadstage/HUD-image work, which is seconds and differs per machine.
  Whoever is ready first runs the countdown alone and starts racing into a car
  that is still parsing zip files. There is no "ready" handshake. (The tick
  counters are fine — accepts() compares each sender against its own last tick,
  not against a shared clock — so this is a fairness problem, not a desync one.)

  location.reload() (launcher.js:353). The reload takes down the swarm, the room
  and the lobby, so returning to the game room is impossible by construction 
  today — and each player is dumped to the main menu independently, whenever

  object). It's the one signal that says "this player is on their end screen and
  is no longer really racing" — exactly what a lobby-return flow needs to know
  who's finished.

  Both bugs, one cause

  A netplay race ran at fase = 0, so the transcribed game believed it was single
  player and every fase === 7001 branch of stat() was dead code. main.js now
  sets xt.fase = sync ? 7001 : 0 and xt.lan = !!sync, which fixes:

  - the announcer — plnames[n] instead of cd.names[sc[n]], so it reads the
  player's name;
  - the auto-exit — exitm = 4 (spectate) instead of falling through to the
  "Press [Enter] to continue" hold that dropped you back to the launcher.

  One deliberate deviation at XtGraphics.js:936: the Java reads exitm != 4 || 
  !lan || im != 0, so only the host spectates indefinitely and a guest is
  ejected after 1200 ticks. I dropped the im term — a wasted player waits for
  the race to actually end, whoever they are. Hold lengths and the rest of the
  branch are the original's.

  The rest of the lifecycle

  Disconnects, which nothing handled anywhere. NetPeer.onClose was assigned by
  no one. Now: the host removes a departed guest from the roster and reassigns
  slots; a guest whose host vanishes is told and returned to the list; and
  mid-race playerGone() wastes the car and sets checkPoints.dested = 3, the
  original's own disconnect marker. That last one matters more than it sounds —
  a car nobody transmits dead-reckons forever and never becomes dest, so
  "everyone else is wasted" was unsatisfiable and such a race could never end.

  A gap the swarm rewrite created, which I hit while wiring the above: on one
  swarm the peer connection now outlives both the lobby and the race, so
  quitting no longer fires peerclose. Departures have to be spoken — {t:'bye'}
  from Lobby.leave() and from leaveRace(). The old room-per-swarm design got
  this for free, which is exactly why it was easy to miss.

  The start is now gated on both worlds existing. The lobby's start was the
  decision to race, not the moment: each client then loads its own stage, HUD
  images and sounds, so the faster machine ran the 3-2-1 alone while the other
  player's car was still an unparsed zip. waitForEveryone() barriers on a ready
  broadcast, re-sent on a timer (a ready arriving while the peer is still in
  boot() reaches the lobby's handler, which drops what it doesn't recognise),
  and times out after 30s rather than stranding everyone on one bad load.

  There was no way out of a networked race at all — at fase 7001 the quit path
  defers to exitm's confirm menu, which lives in the unported mouse-driven
  multistat(). Escape now sets fase = -2 directly, suppressed while the
  end-of-race screen is up so it doesn't steal that Enter.
