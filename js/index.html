Round 3b — splitting the 11.5 ms that ?raster=0 removed

Last round showed draw is ~half projection, ~half "everything else". But raster=0 stubs two unrelated things at once: geometry batching (triangulation, vertex writes) and the Canvas2D overlay (fillText, drawImage for the HUD). Node says the batcher is only ~26% of draw — but node's null 2D context already no-ops the overlay, so node cannot see that half at all. Hence four runs.

B loses the HUD, C and D go blank. Expected — stopwatches, not rendering modes.

Compare the ns/vert submitted line, not ms/frame. Your first run of this came back with the stubbed configs slower than the normal one, which is impossible — the cause was that scene weight swings by ~60% depending on where the car is and what's on screen, and that swamps the differences being measured. The benchmark now counts polygon vertices submitted (counted even when emitting is stubbed, which it wasn't before — C and D reported a scene of zero) and normalises by it.

From the four ns/vert figures: overlay = A−B, geometry = A−C, projection = D. If A−B is the big one, the fix is the HUD overlay and is cheap; if A−C is, it's triangulation; if D dominates both, it's the shader rewrite and nothing else will help much.

Still worth keeping the runs similar: same stage, and either drive all four the same way or — easier — don't touch the keys at all in any of them.

Round 3 — is it projection, or the batcher? (answered: both, ~50/50)

"Draw" is two costs stacked: the per-vertex projection in Plane.d(), and the triangulation + vertex-buffer writes in graphics.js. Only the first can move to a vertex shader, so this decides whether that rewrite is worth doing.

B makes every draw call still happen — so all the projection maths is still paid — but throws the geometry away instead of triangulating it. The screen will be blank in B. That is expected; it's a stopwatch, not a rendering mode. Just let the 6s run.

A — normal, 8 cars B — projection only (blank screen)

If B is still ~20 ms, it's projection and the shader work pays off ~4x. If B collapses to a few ms, the cost is in the batcher and the shader would buy almost nothing — different fix entirely.

Settled — no need to retest

Physics is not the bottleneck. 0.6–1.7 ms/tick. The 10.3 ms figure in WORK.md was sim+draw measured as one.

Resolution is nearly free on the CPU (res=1 24.1 ms vs res=2 24.1 ms); MSAA at 2x cost ~12% and is now off above 1x. GPU fill time is invisible to these timers, so this is a CPU statement only.

fps is pinned to 18.9 whenever interpolation is off — the game draws only on a tick. Don't compare builds by fps in that mode.

Interpolation — the only route past 18.9 fps, but the car jitters and each interpolated frame costs a full ~17 ms CPU redraw. Off by default.

Array pooling — no measurable difference. Dropped.

Frame cap — moot, the machine never reaches 60.
